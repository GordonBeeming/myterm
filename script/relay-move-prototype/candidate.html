Move the account, keep endpoint trust

Can one ordered location change move a personal account between relays while preserving its identity, endpoint approvals and server-owned sessions?

This page runs an in-memory state model. Passkey ceremonies, encryption, network delivery, disk durability and terminal continuity are simulated. The separate Node harness uses real Ed25519 signatures for message-binding checks. Neither establishes a production migration protocol.
1 · Reserve and prepare
Destination passkey, empty account, compatible features and a durable staged transfer.
2 · Commit once
Explicit endpoint approval and source passkey, or the accepted explicit unavailable-source override. The existing ordering server signs the location change.
3 · Finish and discover
Activate the destination, obtain fresh relay sessions and publish bounded forwarding. Retry the same commit after interruptions.

    Proposed protocol

    Trust and signed messages

    The personal account anchor and ordering-server identity stay the same across relays. Every move is an account-management operation in the existing ordered journal. An approved endpoint requests it; the current ordering server validates membership, approval and the exact preceding checkpoint. The relay cannot appoint a replacement authority. If the ordering server is unavailable, the move waits.

    A destination-issued ticket binds the protocol version, random move ID, source account anchor, prior location receipt, destination relay origin and pinned service identity, destination account ID, transfer public key, required feature digest and ticket expiry. The destination signs those exact fields. The trusted endpoint confirms the destination through its verified HTTPS origin, binds its service key, and first authorizes export to that exact ticket. After staging, a second endpoint confirmation signs the ticket digest and exact transfer manifest. Hostname strings supplied by the source alone do not establish destination identity.

    The normal path also requires a fresh source-passkey assertion bound to the exact ticket digest, predecessor checkpoint and a fresh single-use challenge/expiry before export, including its destination, account and transfer key. Final endpoint confirmation separately binds the staged manifest before commit. Destination and source assertions use their respective relying-party identities. The destination passkey remains the destination login credential; source credentials are not transplanted. Passkey sign-in alone does not confer endpoint approval. Ceremony adapters are fixtures in this prototype. Real passkey challenge consumption and export-grant nonce consumption remain integration work; a signed nonce alone does not demonstrate single-use enforcement.

    After validating the staged transfer, the destination signs a prepared receipt over the ticket and manifest digests. Final endpoint approval confirms the staged manifest; the ordering server serializes a location commit binding the ticket, manifest, prepared receipt and preceding account checkpoint. Request IDs make retries idempotent. Competing requests with the same predecessor cannot both commit. This extends the agreed honest, non-rolled-back ordering-server assumption; it does not eliminate that protocol's fork/freshness limits.

    Commit, cancellation and retry

    1. The destination atomically reserves an empty account for one move, checks registration and compatibility, and stages a manifest-verified transfer. A retry of the same ticket returns the same state; another account or ticket cannot reuse that reservation.
    2. After source authentication and endpoint export authorization, freeze the source relay's account-state writes and capture a final encrypted-record watermark. Local/direct terminal activity continues. Publications after the watermark must be buffered at trusted publishers and replayed at the destination. Prepared data stays reserved through uncertain delivery; it must not disappear merely because the ticket expires.
    3. Before the ordered commit, cancellation requires an ordered abort/tombstone, allowing the destination to release its reservation and the source to resume writes. The authority checks ticket expiry at commit. An expired uncommitted ticket needs a new ceremony. An abort cannot race past a committed location change.
    4. The authority persists the complete location commit before acknowledging it. From this point the destination is the account's logical home. A lost acknowledgement requires querying/replaying that same commit, never a rollback. Destination activation may still be pending, causing temporary relay unavailability.
    5. The destination activates only after verifying the ordered commit. Fresh destination sessions replace source relay tokens. After activation acknowledgement, the source removes active transfer data under the deletion/backup policy and retains only authenticated forwarding material. The old relay must validate current ordered location before accepting account mutations; if unable to do so, it cannot safely remain writable.
    6. A later move is a new forward operation from the latest committed location. A committed destination lost before recovery is a further outage case, not permission to revive the old home. Production crash recovery must exercise every durable boundary; in-memory retries here do not prove disk or distributed transaction behavior.

    Unavailable source and offline endpoints

    Agreed: an unavailable-source move must involve the existing ordering server, and its destination account must be empty. Gordon also accepted the explicit override: destination passkey sign-in, approval from one trusted endpoint and that server may authorize a move without a source-passkey assertion or a second approving device. The accepted risk is that an attacker able to use an approved endpoint’s trusted identity could invoke this path. This is an explicit fallback ceremony, not an automatic downgrade after a timeout. If the source returns, the signed ordered move fences it. The claim that the source is gone is user-declared; it is not cryptographically provable. One endpoint plus the existing authority may explicitly override source-passkey confirmation; this is an accepted trust boundary, not proof that an outage occurred. Whenever the source cannot obtain current authority state, including an authority outage before or after preparation, it must remain fenced for account writes until a commit or ordered abort is verified.

    The fallback can transfer only ciphertext, history and envelopes available from trusted endpoint caches or another verified replica. Relay-only queued content changes may be unavailable. Missing security state is never restored by guessing: preserve the authority’s verified revocation history, and keep any single-use invitation whose winning allocation cannot be verified unusable until its original issuer can reconcile it or a new credential is issued. A user’s acceptance of lost content cannot authorize replay of spent invitations. This is a required fail-closed rule, not a tested credential-reconciliation implementation. Gordon accepted proceeding with available verified copies after explicit acknowledgement that newer content may be irrecoverable, including changes the app cannot enumerate. This acknowledgement is bound to the current move ticket and must be renewed if the available transfer changes. The prototype demonstrates this path separately from the hard stop for unverified security state. It does not claim to recover inaccessible data.

    Returning endpoints start with their pinned account anchor, verified authority configuration and checkpoint. A relay forwarding response is a discovery hint. Before following it, verify the contiguous ordered history, destination/key bindings, membership changes and a destination-signed activation receipt. Reject stale history, a conflicting extension or an unknown authority; fetch missing chain segments. The signature fixture checks a single location extension and activation receipt; full authority-configuration changes, membership propagation and multi-hop cryptographic validation remain integration work. A manual URL alone proves nothing. A valid but withheld newer move remains subject to the accepted freshness limitation.

    Each source retains its own forwarding receipt for fourteen days by default, configurable by that operator. Later moves never extend earlier expiries. The destination and trusted endpoints retain continuity evidence beyond those source TTLs. Endpoints returning after expiry need a manually supplied destination or a reachable trusted endpoint. New deployment instances with only a dead bootstrap address also need an updated address; credential continuity does not imply location discovery.

    Review gates

    Accepted through live discussion: require the existing ordering server; reject an occupied destination account; allow the explicit source-passkey override using one trusted endpoint; allow fallback from available verified content after explicit loss acknowledgement. Security state must still be verified. The prototype direction is selected; production protocol composition and acceptance remain follow-up work.

    Implementation workstreams after acceptance: signed move records and location checkpoints; destination reservation/staging plus durable recovery; source authorization/export/fencing and deletion-safe cleanup; endpoint discovery and fresh relay admission; credential bootstrap continuity; native fault, privacy and integration acceptance. These are proposed follow-ups, not completed work. Returning-endpoint relay admission still needs a concrete protocol: encrypted membership alone is not readable authority for a destination relay. The destination must validate a scoped grant from the moved account authority and endpoint key possession without treating relay sign-in as endpoint approval. That composition is not tested by this model.

    Validation limits: the reducer assumes verified messages, honest endpoints and one current authority. It models reachability as switches and persistence as retained memory. Node checks independently sign and verify selected message fields. Passkeys, HPKE/AES-GCM transfer composition, real relays, key stores, byte-level framing, native platforms, real terminals, partitions and crash persistence remain untested here. Production security review remains required.
