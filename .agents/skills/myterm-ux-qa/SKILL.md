# MyTerm UX QA

1. **Set up real test surfaces.** Use [test-myterm](../test-myterm/SKILL.md) for builds, signed companion pairing, device control, and permissions. Record the commit, build settings, platform, OS, and profile. For a release candidate, exercise the Mac and companion builds together over a live relay. For the Duo, cover folded and unfolded layouts, rotation, and navigation between sizes when available. Mark unavailable device modes or environments as unverified.
2. **Inventory screens before capture.** List every reachable screen, pane, settings page, menu, sheet, and meaningful state on each platform. Include first run, populated content, loading, errors, disconnected states, and destructive action confirmations where applicable. Give each surface a stable identifier. Group related surfaces into batches such as setup, workspace navigation, terminal control, browser, and settings.
   Capture light and dark appearances. Quit the QA Mac client before relaunching its development bundle with `open -n dist/rust-workspaces/myterm-dev.app --args --qa-appearance dark` (or `light`). This changes appearance for that run only. On the dedicated simulators, use `xcrun simctl ui <UDID> appearance <light|dark>`. Wait for sheets, appearance changes and device transitions to settle. Scroll to reveal the complete control when a page extends beyond the viewport. Verify WCAG AA contrast for normal text (4.5:1), large text (3:1), and meaningful control boundaries or state indicators (3:1). Use measured colors for custom styling. Visually inspect system styling, keyboard focus, and states that use more than color alone.
3. **Use safe evidence data.** Keep the exact production-configuration rehearsal private. Use a separate demo copy for screenshots, retaining the relevant folder, workspace, and pane structure. Rename folder, workspace, and tab labels. Replace client URLs, paths, histories, and other identifying values. Put active test content in a Demo workspace. Inspect every capture before sharing it. Keep pairing codes, setup links, credentials, and client information out of captures, model inputs, and the PDF.
4. **Review in parallel.** Give the same complete area batch to the latest available Fable and the latest available Astra. Use the current Fable alias or newest supported Fable model with the cross-agent runner, and the newest Astra offered by the agent runtime. Record model identifiers or aliases and the capture manifest. Ask both for a separate Accept or Needs change verdict per surface, concrete evidence, and a suggested fix. Keep reviews independent. Record tool or model gaps explicitly if either reviewer cannot see the images.
   Ask for platform-native polish. On Mac, check pointer and keyboard use, menus, and window layout. On standard iPhone, check compact navigation and reachability. On iPad, check columns and multitasking widths. On Duo, check both sizes and whether selection, orientation, and focus survive folding and unfolding. An app can work correctly and still need a UX change.
   Check each label and control for a clear purpose. Use recognizable system icons with accessible labels. Keep the primary action and any warning it needs visible; move longer explanations into help. Apply [Apple’s iPhone Duo guidance](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo) to custom layouts near the fold and reserved regions.
5. **Fix and recapture by area.** Reproduce findings on the real surface. Fix the verified issues together, run relevant regressions, and recapture every affected surface. Send the fixes and fresh batch to both reviewers, with prior findings identified. Run at most five rounds per area, counting the first critique. Close an item when both reviewers accept it. At the cap, retain unresolved findings with platform, screenshot, impact, and reason. An unavailable reviewer or missing capture stays unverified.
6. **Report readiness separately from critique.** For each surface, record the last-round screenshots and both verdicts. Also record actual Mac workflow, live phone and iPad pairing/control, configuration-upgrade results, simulator versus physical coverage, and any failures or gaps. For a requested evidence PDF, use the PDF skill and verify rendered pages. Return opted-in diagnostics and other test settings to their original state. Release authorization is separate from QA.
