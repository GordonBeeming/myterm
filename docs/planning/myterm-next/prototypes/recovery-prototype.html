MYTERM · PASSKEY RECOVERY

One passkey experience. No separate recovery key.

Agreed product constraint · remaining recovery paths are candidates

Relay authentication stays passkey-only. MyTerm will not ask people to keep another recovery secret. The account records where your servers are. Losing access to it means losing that account; workspace data stays on the servers.

Where the passkey fits

Conceptual explanation only. No passkey, encryption or recovery operation runs here. A server still needs independently verified authority before it trusts a replacement client; relay login alone cannot protect admission against a malicious relay.

What this means when things are lost

Phone lost; passkey still usable

Sign in on a replacement client. Restore private trust through a validated passkey-unlock design or approval from an existing trusted endpoint. No separate recovery code.

All passkeys and clients lost; disk survives

There is no remaining relay login credential. Local administrative access may preserve files and let the owner rebuild server trust. There is no requirement to restore the lost account. A new account starts with ordinary setup.

Server disk lost

The passkey may still sign in. Files need a workspace backup, and live terminal processes are gone. A login credential cannot restore the missing disk.

Decision settled

The account is the directory of your servers. Authentication stays passkey-only. If you lose access to the account, you have lost the account. No separate recovery key or account-restoration workflow is required.

Account access lost

The old server directory is unavailable. Account loss is an accepted outcome.

Server disk survives

Its workspace files remain on that server. Losing the account does not delete them.

Server disk lost

Recovering files needs a workspace backup. The account is not that backup.

Setting up another account and enrolling servers is new setup. Secure server admission remains a separate design decision; automatic transfer of trust is not implied.

Assumptions that change the answer

The recovery-key candidate wraps directory decryption and account admission authority under a secret kept outside the relay. The offline recovery package includes the key, root identity and wrapped authority backup; a bare key without that backup may be useless. Its root identity must be independently anchored in that recovery material. This is broader than a key that only decrypts directory labels. If we choose that narrower key, the admission benefit disappears.

Trusted clients are assumed to hold directory access and client-admission powers. A server can instead have only its own session authority. Neither option is selected. Each example concerns one server; authority to recover other servers does not follow from access to this server.

Workspace files and saved layout live on the server disk. Live terminal processes and volatile scrollback require the original running process. Saved scrollback survives only if it was actually persisted; that persistence policy is undecided. The demo assumes no separate workspace backup and an otherwise readable disk; disk-encryption keys are a separate requirement.

Relay login and endpoint trust are separate. A recovery key does not recover a lost passkey, force a compromised relay to cooperate, or establish that its directory is current. A usable encrypted backup needs authenticated versions and a trustworthy freshness checkpoint. Those checks, revocation, key rotation and recovery after a stolen key still need design and validation.

During relay loss or compromise, existing pinned direct/local connections may work if independently reachable. They do not require the relay to authorize them. Starting fresh requires independently verified trust. A replacement relay would need its own account setup and routing; this demo does not assume automatic failover.

Privacy boundary and source

This prototype uses the candidate protections and recovery distinctions in the local relay investigation. Encrypting content does not hide the source addresses, live routing relationships, sizes or timing observed by a forwarding relay. That privacy question was unresolved when this historical comparison was made. The later account-trust decision permits connection IPs and account-linked operational telemetry with responsible collection and retention; private directory and workspace content remain protected from the relay.

All state stays in memory. No credentials are requested or stored. Source links open the canonical decisions and research on GitHub.
