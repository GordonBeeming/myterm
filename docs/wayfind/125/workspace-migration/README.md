# Workspace migration and five-backup retention

This is a disposable experiment for [Validate workspace migration and five-backup retention](https://github.com/GordonBeeming/myterm/issues/158). Gordon approved a bounded standalone prototype because the redesigned account-layout store and integrated native migration workflow do not exist yet. The ticket remains open for human review.

## Run it

From the repository root on a Mac with Swift and Python 3:

```sh
python3 docs/wayfind/125/workspace-migration/probe.py --output /private/tmp/myterm-workspace-migration-review
```

The probe compiles `Decoder.swift` with the checkout's actual `Sources/MyTermCore/*.swift`. Every native decode runs against a disposable copy: `WorkspaceStore` can repair and rewrite its input, so it never receives the original source path. All migration files are created in temporary directories. The command does not read the installed app's state, open MyTerm, contact the relay, enroll an endpoint or launch terminal/browser runtimes.

Open `walkthrough.html` directly to explore nine scenarios. Its buttons run a separate JavaScript discussion model; they do not execute the Swift decoder or filesystem candidate.

## Candidate direction

- Recognize explicit schema versions 1 and 2. Use the native decoder, then check its recovery report, source identities and terminal/browser content independently. Version 2 must round-trip without content changes. Version 1 checks recognized fields, workspace and folder content, settings, tab titles and session content, while retaining the complete legacy document for recovery. UUID spelling is normalized for identity comparisons.
- Keep shared folders, workspaces, groups, tabs and content distinct from this client's selection, focus, expansion and display settings. Shared content contains identity and assigned-server references; full terminal/browser payloads live in the separate server-owned runtime records. Bind each terminal/browser identity to the original local server. The receipt includes the assigned server; changing it for already imported content reaches the identity-collision refusal, preserving ownership. The native version-1 conversion supplies new structural identities deterministically where its schema needs them.
- Reject lossy arrays, repairs, conflicting identities, unsupported versions and unknown fields. Stop rather than silently completing a partial migration. This is a conservative candidate, not a general repair/import tool.
- Preserve the original source bytes throughout. Write the complete candidate, client preferences, runtime ownership records and retry receipt in one separate atomic snapshot. The source path, source bytes, account, channel and local server bind the receipt. A retry of a committed operation returns that receipt without adding content again.
- Require explicit additional import when an account layout already exists. Add work without merging by name or changing existing server assignments. This is separate from ordinary first account enrollment, whose approved additive behavior is recorded in [Validate local-first enrollment and workspace merging](https://github.com/GordonBeeming/myterm/issues/162).
- Count both the new slots and recognized legacy `.v1-backup*` / `.recovery-backup*` files toward five automatic copies per state file. At capacity, remove the oldest eligible copy before creating the new one, so a sixth backup staging file is never needed. The legacy-name fixture explicitly pins its pre-v2 copy. The candidate does not infer protection for other historic backups from their filename; unpinned old `.v1-backup` copies are eligible for rotation. Production must reconcile any outstanding legacy recovery requirement before retiring those copies. Existing sets larger than five are reduced before adding a copy; that pre-existing excess cannot be undone retroactively. If protected copies prevent rotation, stop.
- Flush the backup and directory, then record its protection in a durable pin file before committing the destination. Keep it protected across interruption and failed writes. Release pins only after successful commit, or when restart loads the committed receipt. The old target receives its own backup before an additive import changes it.
- Use cooperative OS file locks for the source and destination migration paths. An uncertain directory-sync failure ends the migration invocation. Restart reloads the snapshot before any further write.

`migration.py` is a candidate transaction adapter, not a replacement for the accepted replicated-layout protocol. Its single JSON envelope demonstrates a storage boundary. Production must commit migration admission and retry evidence through the real encrypted layout/trust machinery; no central online authority or new availability requirement is selected here. Snapshot absence never creates deletion evidence, and this candidate has no runtime cleanup path.

Coverage includes duplicate JSON-key rejection, changed source-channel/account inputs and refusal to reassign already imported content to a different server, both channel paths, supported versions, native repair detection, full terminal/browser content comparisons, stable identities, local preferences, server bindings, exact retries, same-name workspaces, identity conflicts, existing account preservation, private target permissions, cooperative lock contention, backup limits, legacy backup names and durable pins.

A child process exits at named boundaries during the backup write, before snapshot commit and after commit but before acknowledgment. An incomplete copy has a `.partial` name, occupies the reclaimed slot and is removed on retry before creating a ready backup; no receipt can treat it as a complete copy. Real read-only target directories produce permission failures while creating the migration lock; this does not establish a native commit-time write failure on a read-only volume. Named injections exercise backup partial writes, validation refusal, `ENOSPC`, failed replacement and uncertain post-replacement directory sync. The checks verify that the expected failure/exit was reached and restart does not duplicate the candidate's records. The ring probe repeatedly rotates other copies while an interrupted migration's recovery copy remains pinned. Five interrupted attempts with changing sources deliberately exhaust the protected slots and stop the next attempt. Rotation at capacity reclaims an eligible old copy first; if writing then fails, one fewer eligible backup remains. The walkthrough shows that tradeoff while the source and protected copies survive.

## Boundaries still requiring production acceptance

The fixtures cover a selected split with a terminal and browser, a folder, display settings, selection and focus, plus a second server's distinct identities. A separate multi-tab version-1 fixture also exercises an inactive split. Its source and converted structures are recorded: the existing native converter preserves content identities but flattens inactive split content into tabs in the focused group. That structural rewrite needs explicit review when choosing the production migration behavior. They do not cover every historic layout shape, agent-conversation field, setting or browser profile. Version-1 full-fidelity acceptance needs a wider fixture corpus, including more nested and mixed layouts and supported agent recovery. The native decoder's current conversion behavior is the reference here; retaining a legacy document does not prove every field is represented in live shared state.

The disposable account snapshot does not implement causal history, tombstones, encryption, membership authorization, key storage or returning-member reconciliation. The entire legacy document is retained only in the client-local portion for this experiment; production must define secure retention and avoid publishing local settings into shared layout. The experiment cannot establish that its field classification covers every future client preference.

The probe never creates a MyTerm terminal or browser runtime. Duplicate-free ownership records are established, but uninterrupted real-process ownership, browser sign-ins and native Settings workflows are unverified. Production channel separation and the full account bootstrap must be tested in the integrated apps.

A named `ENOSPC` or sync exception is an injected failure, not an actual full volume, hardware error or power-loss experiment. Process exits run on a healthy macOS filesystem. Platform-specific durability and recovery after actual power loss remain unverified. Channel-path checks in this adapter recognize the app's normal filenames; arbitrary scratch paths use the caller's channel argument. Production must choose paths through its real channel resolver. The candidate uses cooperative locks; it does not quiesce the current app's live writer, defend filesystem paths against a hostile same-user process, or reconcile a backup restored with old trust state. A source change detected before commit stops. After commit, edited or reserialized source bytes with the same identities also stop on a collision instead of updating imported work. Production needs a supported handoff from the old writer to prevent late changes and define recovery for that case.

Pins for an abandoned source/account attempt deliberately remain protected until that attempt is recovered or explicitly abandoned. Production needs a safe recovery/abandonment workflow and validation of existing pin/backup metadata before retiring anything. Locks, pin files and the target envelope are experiment mechanisms, not a selected production disk format.

No ticket resolution, production source change, release or shared deployment is implied by this checkpoint. The research branch is retained and never merged.
