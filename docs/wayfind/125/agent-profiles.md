# Agent profiles and conversation recovery

Research for [Establish agent profile and conversation recovery support](https://github.com/GordonBeeming/myterm/issues/204).

Codex and Grok Build have per-launch homes that select their local conversation stores. Antigravity documents exact-ID recovery. Its terminal launcher has no documented signed-in profile selector, although the installed ACP subcommand can use a separate local data directory.

## MyTerm baseline

MyTerm's Claude recovery records the conversation ID and the effective `CLAUDE_CONFIG_DIR` reported by that conversation's hook. On recovery, MyTerm supplies the saved directory to `claude --resume <id>`. The bare command still handles the standard sign-in and older saved handles. The badge can show the organization or a profile label. The PR reproduced terminal-host loss with isolated app state and reopened the same conversation. Its behavior for unusable paths falls back to the bare command. [Resume Claude under its own profile and keep its account badge](https://github.com/GordonBeeming/myterm/pull/203)

The launcher is the command MyTerm invokes. The profile is the effective local settings or conversation store. Sign-in is the account or credential route the CLI uses at the time. The conversation ID identifies the thread within the store or service that can load it. A launcher and a login status each supply only part of that information.

## Documented behavior

### Codex

- `codex` is the standard CLI. MyTerm also records whether its `codex-statusline` launcher started a session. OpenAI's `--profile <name>` selects a configuration layer in `$CODEX_HOME/<name>.config.toml` as of 0.134.0. The named settings layer lives within the selected home. Supply `CODEX_HOME` for another home, or omit it for `~/.codex`. The upstream resolver canonicalizes the explicit directory and rejects an ordinary path that is missing or points to a file. [MyTerm's launcher and recovery code](https://github.com/GordonBeeming/myterm/blob/5f1a467e54ac03abdef93c0423ef23be3f3fa6b8/Sources/MyTermCore/AgentSessionRecovery.swift), [Codex configuration profiles](https://learn.chatgpt.com/docs/config-file/config-advanced), [Codex 0.170.0 home resolver](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/utils/home-dir/src/lib.rs#L5-L59)
- `codex login` supports ChatGPT OAuth, device auth, API keys and access tokens. The file backend stores `auth.json` in the selected home. The operating-system credential backend in 0.170.0 keys its entry by a hash of the canonical home. Codex also supports automatic fallback to a file and process-only storage. Separate homes give Codex distinct cached credential locations with the file and keyring backends. The active account can still change within a home. [Codex authentication](https://learn.chatgpt.com/docs/auth), [Codex 0.170.0 credential storage](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/login/src/auth/storage.rs#L307-L389)
- The hook supplies `session_id`, `cwd`, model and an optional transcript path. With local persistence, Codex reads session rollouts under the selected home. Resume with the saved launcher and effective home using `codex resume <id>` from the original working directory. Preserve an explicit named configuration profile when its settings are part of the original launch, including any model provider it selects. An explicit `--remote` app-server launch is a separate case. Its thread must be looked up on that server. [Codex hooks](https://learn.chatgpt.com/docs/hooks#common-input-fields), [Codex 0.170.0 rollout lookup](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/rollout/src/list.rs#L347-L372), [Codex CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli#codex-resume)
- For a badge, use a user-chosen label for the home or settings profile. `codex login status` reports the current authentication mode. The App Server's `account/read` can report current account and plan details, while `account/updated` can report changes. That is a candidate for opt-in display metadata if queried in the same launch context. A later account read cannot establish who started an earlier conversation. [Codex CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli#codex-login), [Codex App Server](https://learn.chatgpt.com/docs/app-server)

### Antigravity CLI

- `agy` uses settings under `~/.gemini/antigravity-cli/settings.json`. It can use a saved OAuth sign-in, Google Cloud or advanced SSO sign-in. Setting `modelProvider` to `gemini` and supplying `GEMINI_API_KEY` sends requests directly to the Gemini API without a Google account session. With that provider configured, a missing key prevents startup. `--project` selects an Antigravity project, and `--remote-agent` selects where the conversation runs. Google's CLI reference does not document an account or separate user-home flag. Google's troubleshooting guide describes OS credential stores, so a different configuration directory alone would leave credential isolation unproven. [CLI settings](https://antigravity.google/docs/cli/using), [Authentication](https://antigravity.google/docs/install?tab=cli), [CLI reference](https://antigravity.google/docs/cli/reference), [Credential storage troubleshooting](https://antigravity.google/docs/cli-troubleshooting)
- The status-line JSON provides `conversation_id` (also `session_id`), working directory, conversation title once assigned, and model details. The CLI header can display an email or the Gemini API key mode. The published status-line schema provides no account identity field. A user-chosen launch label can be displayed without reading a transcript or scraping the header. [Status line payload](https://antigravity.google/docs/cli/statusline), [Authentication display](https://antigravity.google/docs/install?tab=cli#using-a-gemini-api-key)
- Start from the original working directory and use `agy --conversation <id>` for a local conversation. The CLI chooses the associated project during resume. Remote-agent conversations live with their remote projects and require `agy --remote-agent --conversation <id>`. `agy -c` consults a last-conversation cache keyed by working directory and may start a new session if it cannot recover the cached one. That makes it unsuitable for restoring a specific pane. Once the original account or route is unavailable, exact-ID recovery should stay unresolved until the user restores access. [Resume command](https://antigravity.google/docs/cli/commands/resume/), [Projects](https://antigravity.google/docs/projects?tab=cli), [Remote Agents](https://antigravity.google/docs/remote-agents/)

### Grok Build

- `grok` opens Grok Build. `GROK_HOME` selects its home and user config. The default is `~/.grok` on macOS and Linux and `%USERPROFILE%\.grok` on native Windows. Project settings belong to the repo layer. `--sandbox <profile>` selects filesystem containment and can change which daemon session store is visible. The installed `grok agent` also exposes `--agent-profile` for agent settings. Browser sign-in, device sign-in, an external auth-provider command, or an API key can supply authentication. Credential precedence can vary by model. The 1.0.92 bundled authentication guide identifies `~/.grok/auth.json` for the default home. Browser credential isolation under alternate homes remains unverified. [Grok settings](https://docs.x.ai/build/settings), [CLI reference](https://docs.x.ai/build/cli/reference), [Authentication methods](https://docs.x.ai/build/enterprise#authentication)
- Grok documents on-disk sessions keyed by working directory and exact recovery with `grok --resume <id>`. Use the original working directory and selected `GROK_HOME` for a non-default launch. The workspace picker, bare `--resume`, and `-c` are discovery or recency controls. Grok's sessions and headless pages give different descriptions of `--session-id` reuse. MyTerm can use the documented exact-resume flag and avoid depending on that distinction. [Grok sessions](https://docs.x.ai/build/features/sessions), [Grok sandbox](https://docs.x.ai/build/features/sandbox), [Headless and scripting](https://docs.x.ai/build/cli/headless-scripting)
- Grok hooks report the session ID and working directory, and pass `GROK_SESSION_ID` to command hooks. Headless JSON also reports the session ID. The published hook and status-line payloads provide no account identity. A user-chosen home label remains displayable without reading browser credentials or inferring an account from a model or API route. [Grok hooks](https://docs.x.ai/build/features/hooks), [Grok status line](https://docs.x.ai/build/features/status-line), [Grok sessions](https://docs.x.ai/build/features/sessions)

## macOS probes

The probes ran on macOS 27.3 arm64 with temporary homes and working directories. They inherited no sign-in environment. Each CLI also ran with its defaults inside the temporary home. No account or model turn was used.

| CLI | Default and alternate launch | Missing profile or conversation |
| --- | --- | --- |
| Codex CLI 0.170.0 | The default and alternate `CODEX_HOME` each started the local App Server. In the alternate home, `codex -p isolated mcp list` listed an entry defined only in `isolated.config.toml`. The app server could create and read a thread in-process without a model turn. | A `CODEX_HOME` path that did not exist stopped startup. A missing named profile produced the base result in `mcp list`. `thread/resume` reported a missing rollout for an unknown ID in both homes. The empty thread did not survive an App Server restart even in its original home, so that probe cannot establish successful recovery. |
| Antigravity CLI 1.5.9 | `agy acp` initialized with the default directories and with relative `--gemini-dir` and `--app-data-dir` values. The alternate launch created a separate configuration and conversation directory beneath the temporary home. These flags were listed for ACP only. | The ACP language server rejected an absolute `--app-data-dir`. A missing `--settings` file was rejected. Both available ACP data directories returned `Authentication required` for `session/load`, so conversation lookup and credential isolation remain unverified. |
| Grok Build 1.0.92 | `grok sessions list` used the default or supplied `GROK_HOME`, creating its docs and log directories there. An empty home had no sessions. Cloud listing reported an auth error. | Grok created a missing `GROK_HOME`. ACP `session/load` reported `Path not found` for an unknown ID in both the default and alternate homes. ACP `session/new` required authentication. |

To reproduce Codex's profile-loading check, put a harmless MCP entry in `<existing-codex-home>/isolated.config.toml` and compare `CODEX_HOME=<existing-codex-home> codex -p isolated mcp list` with `-p missing`. The probe used `/usr/bin/true` as the listed command and never launched it. For Antigravity, run `agy acp --stdio --gemini-dir myterm-profile-gemini --app-data-dir myterm-profile-data` with a fresh home. For Grok, compare `grok sessions list` with and without `GROK_HOME` and use `grok agent --no-leader stdio` for the direct ACP check. The ACP clients sent `initialize` and requested `session/load` for an arbitrary UUID in the scratch working directory.

Positive recovery from a persisted, signed-in conversation after a CLI restart still needs native confirmation with disposable accounts. For Grok, include the exact sandbox selection when it changes the daemon's session store and verify which credential routes follow the home. For Antigravity, test the normal terminal launch separately from ACP before assuming the data-directory flags are useful to MyTerm.

## Recovery options for the decision ticket

Keep the launcher, conversation ID, working directory and the effective supported store selector together on the MyTerm server that owns the terminal session. Store absolute profile paths only in local state on that server. Keep credentials, transcript paths and unrelated environment variables out of both recovery evidence and synchronized state. If a badge is needed away from the server, a user-chosen label can be shared without making its local path or account email part of the account layout.

For a known non-default launch, resolve the same server-local profile before sending an exact resume command. If the profile disappeared, the saved ID cannot be found, or a detectable sign-in mismatch blocks access, leave the pane at a shell with the handle available for retry. Default and older handles can retain their current exact-ID command. Install or detect hooks in the effective configuration. The current MyTerm installer targets the default Codex, Grok and Antigravity paths, and its activity marker carries a profile only for Claude. For Codex and Grok, compare recording an allowlisted selector at launch with reading it from the exact foreground process. A hook that reports a session ID does not by itself prove which home or sign-in the process used. [MyTerm hook installer](https://github.com/GordonBeeming/myterm/blob/5f1a467e54ac03abdef93c0423ef23be3f3fa6b8/Sources/MyTerm/Models/AgentHooksController.swift), [MyTerm hook reporter](https://github.com/GordonBeeming/myterm/blob/5f1a467e54ac03abdef93c0423ef23be3f3fa6b8/Resources/myterm-agent-hook)

Linux and Windows were outside the local check. Platform-specific credential isolation, missing-profile behavior and MyTerm process or hook integration require native verification. On Antigravity, Google lists Apple Keychain, Linux Secret Service over D-Bus, and Windows Credential Manager. Grok documents both native Windows and WSL, which use different home and shell conventions. [Codex platform support](https://github.com/openai/codex#quickstart), [Antigravity troubleshooting](https://antigravity.google/docs/cli-troubleshooting), [Grok platform support](https://docs.x.ai/build/overview#requirements), [Grok settings](https://docs.x.ai/build/settings)
