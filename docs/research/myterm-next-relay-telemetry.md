# Relay telemetry and retention options

Research for [Establish relay telemetry and retention options](https://github.com/GordonBeeming/myterm/issues/144), 7 November 2026 AEST. The policy source is the [final relay account operations resolution](https://github.com/GordonBeeming/myterm/issues/134#issuecomment-6703620724). Findings below separate documented product behavior, proposed design and decisions still needed. No provider was selected, service provisioned, secrets accessed or deletion mechanism tested.

## Recommendation for consideration

Start with a queryable local store for account-linked operational events, a separate short-lived IP diagnostic store, and optional OpenTelemetry export of aggregate service metrics. Investigate SQLite for the single-instance deployment first; PostgreSQL becomes a candidate if hosted write volume or concurrency justifies operating another database. Keep account-linked events out of external telemetry by default until the deletion contract is settled and the chosen provider's behavior is validated.

Grafana Cloud and Azure Monitor are candidates for a later aggregate-metrics investigation. This report evaluates their log products; metrics pricing, retention and cardinality limits remain unresearched. Loki offers a familiar path to self-managed log search if that later becomes useful. Azure Monitor/Application Insights is credible where an existing Azure operating model makes its query and access tooling valuable, but its documented deletion behavior needs particular care. A complete Loki deployment adds operational work that the initial finite event schema may not need.

This recommendation reduces the number of account-linked copies and gives self-hosting useful diagnostics without a paid service. It still needs implementation and deletion testing. A SQL `DELETE`, an empty search result and physical removal from every storage copy are different claims.

## Agreed boundary and interpretation

The operations resolution permits an opaque account ID, event type, outcome, duration and software version for connection, authentication, enrollment, migration and error diagnostics. The records remain account-linked. It excludes names, client/server names, addresses, private directory/workspace data, terminal/browser content, credentials and keys. Retention is configurable by age or size with no fixed privacy-driven expiry. Raw connection IPs belong in a separate abuse diagnostic store for at most seven days, accessible only to operators who need it. Active account data must be deleted within 24 hours, backup copies must expire within 30 days, and restores must preserve completed deletions; self-hosting can configure these periods. The resolution explicitly leaves reconciliation of diagnostics with account deletion to implementation. [Policy source](https://github.com/GordonBeeming/myterm/issues/134#issuecomment-6703620724).

Recommended interpretation for confirmation: treat account-linked diagnostic records as account data for deletion, even when ordinary age cleanup would retain them longer. Do not claim that replacing the account ID with a hash or deleting its lookup makes retained events anonymous. Define whether “remove active data” requires physical removal from online database/log storage within 24 hours or permits inaccessible residual pages until controlled reclamation. The backup allowance should not silently become an allowance for queryable online copies. No examined managed service documentation establishes every part of MyTerm's proposed contract.

## Provider and architecture comparison

| Candidate | Operational value and deployment | Cleanup and account deletion evidence | Assessment |
| --- | --- | --- | --- |
| Local structured event store, optional OpenTelemetry | Small fixed schema supports account history, outcome counts and durations without full-text search. SQLite suits the required single-instance example; optional collector/export avoids a mandatory external account. | MyTerm must implement deletion, bounded queues, age/size cleanup, backup expiry and restore filtering. Database reclamation needs explicit verification. | Recommended first implementation investigation. Lowest number of copies; more application-owned query and deletion work. |
| Self-managed Grafana Loki + Grafana | Central log search and dashboards; same event vocabulary can be collected through OpenTelemetry. Adds collector, Loki, Grafana and storage operations. | Deletion uses a compactor after a cancellation period, default 24 hours. `filter-only` hides results without deleting storage. The default `filter-and-delete` mode also removes stored entries; deletion requires compactor retention and a delete-request store. Use TSDB for new deployments. Changing the cancellation period alone supplies no completion guarantee. [Deletion documentation](https://grafana.com/docs/loki/latest/operations/storage/logs-deletion/). | Credible optional deployment, conditional on a measured deletion budget and operational ownership. Default configuration cannot establish a 24-hour completion promise. |
| Grafana Cloud Logs | Managed Loki-backed search reduces storage operations; stack-scoped write/read/delete credentials are available. | Submitted deletions immediately disappear from search, while physical deletion runs in background batches every 24 hours. Exported archive copies require separate deletion. This cadence is not a documented worst-case completion SLA. [Cloud deletion](https://grafana.com/docs/grafana-cloud/send-data/logs/delete-log-lines/). | Account-linked logs need vendor confirmation and validation of deletion, internal backups and restores. Aggregate metrics require separate product research. |
| Azure Monitor/Application Insights | KQL investigation and Azure permissions are useful for an Azure-operated service. Self-hosted relay software would still need a local diagnostics option. | Delete Data marks records deleted without physical removal; typical completion is minutes, but requests can queue up to five days. Purge has a formal 30-day completion SLA. [Delete Data behavior](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/delete-log-data#how-the-delete-data-api-works), [purge SLA](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/personal-data-mgmt#purge-personal-data). | Public documentation does not substantiate the required 24-hour account-linked deletion guarantee. Investigate aggregate-only use or obtain a different confirmed contract. |

These are evidence gaps, not claims that a provider can never meet a negotiated requirement. A vendor's recoverability statement or normal retention period does not establish its internal backup expiry or restore suppression behavior.

For self-managed Loki, retention removes index references and sweeps chunks asynchronously; preserve deletion markers across restart. Object-store lifecycle must be coordinated with Loki retention. [Loki retention](https://grafana.com/docs/loki/latest/operations/storage/retention/). Disk-size cleanup also needs separate ownership: the filesystem store does not delete according to disk pressure. [Filesystem storage](https://grafana.com/docs/loki/latest/operations/storage/filesystem/). Avoid making the account ID a Loki label: high-cardinality labels create many streams. Keep it in the structured body if this backend is adopted. [Label cardinality](https://grafana.com/docs/loki/latest/get-started/labels/cardinality/).

Azure Delete Data allows ten requests per hour and requires Analytics-plan tables; Basic tables need a plan change, and Auxiliary tables are unsupported. Purge is limited to 50 requests per hour and is authorized only for GDPR-required requests, so it is not a general-purpose cleanup path. Microsoft prefers ingestion transformations or reduced identifier exposure over later deletion. [Delete Data constraints](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/delete-log-data#considerations), [purge restrictions](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/personal-data-mgmt#purge-personal-data). MyTerm must still treat its opaque account ID as account-linked.

For a relational store, deletion also has storage consequences. PostgreSQL keeps deleted tuples until vacuum; ordinary vacuum makes space reusable and is not a complete erasure guarantee. [PostgreSQL VACUUM](https://www.postgresql.org/docs/current/sql-vacuum.html). SQLite's `secure_delete=ON` overwrites deleted ordinary-table content, with limitations for virtual/shadow tables. WAL, journals, snapshots and storage-layer copies still need separate handling. [SQLite secure deletion](https://sqlite.org/pragma.html#pragma_secure_delete). A WAL checkpoint normally recycles the file without truncating it, and readers can prevent completion. [SQLite WAL](https://sqlite.org/wal.html). These facts make local control useful, but do not turn either database into a tested deletion solution.

## Costs and sizing

Current first-party pricing pages were checked on 7 November 2026 AEST. This report deliberately omits numerical subscription prices: no verified Australian-region quote or dated currency conversion was obtained. An A$ monthly total would therefore be misleading. The following are verified billing drivers and explicit sizing assumptions, not estimates of actual MyTerm traffic.

Grafana Cloud currently includes a free Logs allowance of 50 GB ingested per month with 14-day retention; its paid plan includes 30-day log retention, a platform fee and usage charges for processing, writing and retention. Free-plan retention is a product limit, not MyTerm policy, and neither plan alone solves account deletion. [Grafana pricing](https://grafana.com/pricing/).

Azure Monitor bills according to ingestion/table plan, retention and additional features such as queries, exports and alerts. The pricing page exposes region-dependent placeholders in the retrieved rate table, so obtain a quote for the selected Australian region and currency before comparing totals. Data deletion does not undo ingestion charges. [Azure Monitor pricing](https://azure.microsoft.com/en-us/pricing/details/monitor/), [personal-data management](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/personal-data-mgmt).

| Illustrative workload | Uncompressed application payload calculation | What it establishes |
| --- | --- | --- |
| 100,000 operational events/day, 300 bytes/event | 30 MB/day; 0.9 GB over 30 days | A modest local event store is worth measuring before adding a log cluster. |
| 1,000,000 events/day, 300 bytes/event | 300 MB/day; 9 GB over 30 days | Provider ingestion allowances may still accommodate payload volume, but index, envelope and billing measurements differ. |
| 10,000,000 events/day, 300 bytes/event | 3 GB/day; 90 GB over 30 days | Sampling, event frequency and hosted storage operations materially affect cost. |

These use decimal bytes and a 30-day sizing window, not a proposed retention period. Add database indexes, WAL, replicas, backups, collector buffering and provider envelopes. Measure actual encoded bytes and peak reconnect/abuse bursts. Count live and beta separately, then apply the provider's rules for shared allowances; do not assume two stacks each receive the allowance.

Local storage and self-managed Loki still incur compute, disk, backup, network and operator costs. A free hosted tier introduces quotas and service dependence even when the invoice is zero. The cost decision needs event rate, hosted region, retention/size target, alert frequency, recovery expectations and an A$ quote; none was established by this research.

## Proposed exact operational schema

The following is a proposal for the deployment contract, not an expansion of the agreed allowlist by implication. The five approved business fields are retained. Timestamp, schema version and static deployment metadata require explicit agreement as technical envelope fields. Reject unknown fields at the producer and final export boundary.

| Field | Proposed representation and restriction |
| --- | --- |
| `account_id` | Relay-managed opaque account identifier; optional only for pre-authentication or service-wide events where no account is known. Never derive it from a name, passkey, endpoint key or address. Remains account-linked and participates in deletion. |
| `event_type` | Closed enum: `connection.open`, `connection.close`, `authentication.complete`, `enrollment.complete`, `migration.complete`, `error`. Add future values through schema review. |
| `outcome` | Closed enum: `success`, `rejected`, `timeout`, `rate_limited`, `revoked`, `incompatible`, `peer_closed`, `slow_receiver`, `internal_error`. Document allowed event/outcome pairs. Never interpolate error text or peer close reasons. |
| `duration_ms` | Optional nonnegative bounded integer: handshake/auth/enrollment/migration operation time or connection lifetime, according to event type. Use a monotonic clock to measure duration. |
| `software_version` | Relay build version from trusted build metadata, capped length and validated grammar. Never an arbitrary client-supplied user agent. Endpoint versions would be a separate decision. |
| `occurred_at` | Proposed envelope: server-generated timestamp stored in UTC; operator-facing renderings use the configured display timezone. |
| `schema_version` | Proposed envelope: fixed integer `1` for this schema. |
| `service.name`, `deployment.environment.name` | Proposed static resource allowlist: `myterm-relay` and one of `live`, `beta`, `self-hosted`. Prefer deriving the environment from the destination/store configuration. |

No free-text message, nested attribute map, serialized object, arbitrary error type, request ID, trace ID, connection ID, client/server ID, hostname, path, URL, query string, HTTP header, body, user agent, baggage, exception message or stack trace is permitted in this account-event schema. Adding any identifier must state its operational purpose and deletion consequences. Account ID plus timestamp and finite outcomes supports correlation without retaining endpoint names or traffic contents.

Account deletion and suspension events are not included in this proposed enum; decide their diagnostic purpose and treatment before adding them. `error` with `internal_error` is deliberately coarse. If operators cannot diagnose failures with version, timing and event type, propose a finite reviewed error-code extension; do not quietly add `err.Error()`. Pre-authentication failures have no reliable account attribution. Aggregated counts and the separate abuse store cover that limitation.

## Collection, isolation and access

Recommended data paths:

1. Emit account events through a typed producer into the local queryable store. Provide an operator command/API for bounded account/time queries. Ordinary container stdout should receive only approved service-wide diagnostics; copying account events to stdout creates another deletion target in the runtime/journal.
2. Emit service-level counters, duration histograms and resource-health gauges through a separately reviewed OpenTelemetry metrics path. Permit only finite event/outcome/version/environment dimensions. Exclude account labels, exemplars linked to account traces, baggage and per-request identifiers. Aggregation needs review for sparse cohorts and timing correlation; removing an ID is not proof of anonymity.
3. Keep raw IP abuse diagnostics on a separate path, with independent permissions and strict expiry. Never send them through the normal operational export.

Use separate hosted live and beta volumes/databases, collector queues, credentials, backup sets and export destinations. Prefer separate managed stacks/workspaces over a shared store distinguished only by an environment label. An exporter misconfiguration must not send beta account events to live. Self-hosting defaults to local diagnostics, no outbound telemetry endpoint and no vendor credential requirement. Optional exporters are configured by the self-hosting operator.

OpenTelemetry cannot determine MyTerm's sensitive fields automatically. Its Collector offers attribute allowlisting/redaction and transformation processors, but producers and instrumentation libraries still require review. [Sensitive-data guidance](https://opentelemetry.io/docs/security/handling-sensitive-data/). Apply validation before any queue, disk spool or debug exporter can persist a payload, then again before export. Inspect resource/scope attributes, log bodies, span events, span names/status descriptions and metric exemplars; filtering only log attributes is insufficient.

Avoid default HTTP/database auto-instrumentation until its captured fields are verified against this contract. Exception conventions include messages and stack traces and explicitly warn that messages may contain sensitive information. [OpenTelemetry exception conventions](https://opentelemetry.io/docs/specs/semconv/exceptions/exceptions-spans/). Application Insights' default IP masking can still produce city/state/country enrichment, and `client.address` can trigger geolocation. Zeroing the stored IP therefore does not prove compliance with this schema. [Application Insights IP handling](https://learn.microsoft.com/en-us/azure/azure-monitor/app/ip-collection). The current Go documentation marks metrics/traces stable and logs release candidate, so pin and test any logs bridge rather than assuming all Go signals have identical maturity. [OpenTelemetry Go](https://opentelemetry.io/docs/languages/go/).

Restrict diagnostic readers to named operators with a need for access; use MFA, short-lived access where supported, an access-review process and separate privileges for ordinary reads, export and deletion. Restrict local files/volumes and operator query endpoints; protect transport with TLS or a local/private socket. Keep ingestion credentials write-only and deletion worker credentials separate. Never expose telemetry as an account-user browsing interface by accident.

Loki has no built-in authentication layer; an authenticating proxy must set trusted tenant headers and prevent caller spoofing. [Loki authentication](https://grafana.com/docs/loki/latest/operations/authentication/). Grafana Cloud policies can scope read, write and delete actions to a stack. [Cloud access policies](https://grafana.com/docs/grafana-cloud/platform/security-and-account-management/security-and-access/authentication-and-permissions/access-policies/). If Azure is selected, use table/workspace-scoped access and separate deletion permissions, verified against the actual table plan. [Azure deletion permissions](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/delete-log-data#permissions-required).

## Retention, deletion and restores

Proposed operating contract, pending confirmation. The 24-hour active-data deletion and 30-day backup periods are hosted requirements and configurable for self-hosting. Keep the separate raw-IP ceiling at seven days or less:

| Data plane | Routine cleanup | Deletion/backup requirement |
| --- | --- | --- |
| Account-linked operational events | Independently configurable maximum age and maximum bytes; evict oldest records in bounded batches when either configured limit is reached. No policy-imposed fixed age. | Delete the account's records within 24 hours under the confirmed active-storage interpretation. Include indexes, replicas, buffers and exports. Backup copies expire within 30 days. |
| Raw IP abuse diagnostics | Absolute age ceiling of seven days from collection, plus an optional smaller byte cap. | Delete known account-linked entries on account deletion; seven-day ceiling still applies to unattributed entries. Avoid backups of this store, or impose the same seven-day bound on all recoverable copies. |
| Aggregate service metrics | Configurable provider/local retention appropriate to operations. | Review whether any series still identifies an account or small cohort; do not exempt a series solely because it is called a metric. |
| Deletion ledger and jobs | Keep only minimal deletion/suppression state, protected separately. | Survive data restores until every restorable backup, replay queue and export has passed its lifetime. Exact identifier, retention and access remain decisions. |

Use a durable deletion job covering all known copies. First disable access and prevent new account events; atomically record suppression and job state so a crash cannot re-enable ingestion. Purge local rows, queues/spools, replicas, exports, diagnostic bundles and external records; retry idempotently and alert before the deadline. Gate delayed ingestion and replay on suppression state. Track completion per destination and verify by bounded queries; empty queries alone cannot attest physical cleanup. Avoid logging the account ID again in ordinary deletion-worker stdout.

For local storage, test reclamation/checkpoint behavior under long readers and crashes. Encrypt volumes and backups, and document filesystem/cloud snapshot lifetimes. Encryption at rest does not itself establish timely deletion. Per-account encryption with key destruction is another possible design, but requires a decision about acceptable cryptographic erasure and all copies of keys; it was not validated here.

Expire backups no later than 30 days after they contain data due for deletion, including old versions, replicas, snapshots, exported archives and provider-managed recovery copies. Define lifetime from creation and ensure a copied backup cannot restart the clock. A general 30-day operational-log retention setting does not prove backup expiry. Managed providers must confirm these details in writing before account-linked export is enabled.

Restore into quarantine with traffic and exports disabled. Obtain deletion state newer than the snapshot, apply completed deletions to account data and diagnostics, expire IP records using original collection time, and purge buffered records before reopening. If the deletion ledger is restored from the same old snapshot without a newer independent record, completed deletions can be lost. Establish recovery ownership and a fail-closed response when current suppression state is unavailable.

Document cleanup interval, byte accounting, oldest-first eviction, free-space reserve, maximum ingestion queue size, overload/drop policy and alerts for cleanup lag. Logical row caps do not cap WAL, database slack, indexes or container log files. Reclaim storage separately and reserve enough disk to finish cleanup. Telemetry outages should not block terminal forwarding; count dropped diagnostics and expose degraded monitoring without retaining rejected payloads.

## Existing relay evidence

The present Go service provides an implementation seam, not a constraint on the new architecture. At investigated commit `09e00c1750e53e0bc6d94f540c955bafe8d46624`, its README says request logging is deliberately avoided and Caddy access logging is optional. [Relay README](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/README.md#operations).

Existing operational logging must be changed before forwarding it to a telemetry provider. Startup logs include listen/public-origin addresses and raw errors when the relay exits; refresh replay logs include device/request identifiers; transport logs include host/device/connection identifiers and free-text close/error reasons. The close-reason fallback returns `err.Error()`. These exceed the proposed schema even without an HTTP access log. [Exit errors](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/cmd/myterm-relay/main.go#L23), [startup](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/cmd/myterm-relay/main.go#L142), [HTTP API](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/internal/httpapi/server.go#L448), [transport](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/internal/transport/hub.go#L270), [close reasons](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/internal/transport/hub.go#L529).

Inventory reverse proxies, tunnels/CDNs, container runtimes, host journals, crash reporting, application errors and support bundles as separate potential collectors. Disabling app request logs does not configure these layers. The supplied Caddy example does not enable access logging, but an operator's surrounding deployment may do so. [Caddy example](https://github.com/GordonBeeming/myterm/blob/09e00c1750e53e0bc6d94f540c955bafe8d46624/Services/relay/Caddyfile.example).

## Decisions and validation required

1. Confirm that account-linked events follow account deletion, and define acceptable online residual storage handling within 24 hours. Confirm timestamp/schema/resource envelope fields and whether finite error codes are needed.
2. Choose local-only account events or a managed destination after obtaining documented deletion, backup expiry, recovery, region and operator-access terms. Grafana's batch cadence and Azure's documented limits leave a 24-hour assurance gap in the examined material.
3. Specify deletion across account moves: each source/destination copy needs its own owner and suppression/deletion treatment. Forwarding records have their separately agreed lifetime; do not infer that they authorize indefinite diagnostic correlation across relays.
4. Select hosted age/size budgets and self-hosting defaults, plus behavior when storage, cleanup or the provider is unavailable. Decide whether raw IP collection defaults off, and approve its narrow separate schema: proposed `occurred_at`, `client_ip`, optional known `account_id`, finite `abuse_event` (`rate_limit`, `authentication_reject`, `connection_reject`). No URLs, headers, ports, user agents or raw failure payloads.
5. Measure real event rate/size and peak bursts. Obtain A$ quotes for live and beta, including storage, backups, alerts and operator effort. Resolve the deletion ledger's privacy/lifetime and physical-erasure interpretation before committing to a storage layout.

Implementation validation should inject forbidden values into malformed auth requests, peer close reasons and dependency errors, then inspect every emitted signal and queue. Prove live/beta separation, account deletion with delayed export/replay, cleanup under disk pressure, raw-IP expiry and restore of a snapshot predating deletion. For a managed backend, measure physical-deletion completion through the provider's supported evidence and obtain contractual answers for inaccessible internal copies. No such validation was performed during this research.
