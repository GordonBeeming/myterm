One ordering server commits account-management changes. Approved clients and servers own their keys. The relay carries encrypted state and channel records.

    Concrete implementation choices

    Approval

    Proposed eight-digit code, five-minute request, at most five failed attempts. BoringSSL SPAKE2 draft-02 confirms pinned keys, followed by mutual TLS for private approval data.

    Identity and content keys

    Ed25519 identity/TLS key plus one P-256 HPKE key with explicit sender/recipient purposes. Fresh content keys per snapshot/batch; signed private records and per-recipient envelopes.

    Refresh

    Proposed defaults: KeyUpdate after ten minutes or 64 MiB; fresh authenticated connection after one hour or 1 GiB. Automatic scheduling and product handover remain implementation work.

    What remains before production

    Integrate signed Rust account state, admission key-possession/uniqueness checks, native key storage/checkpoints, planned authority transfer, real approval/enrollment transports, encrypted record/version handling and the session attachment protocol. Complete TLS close/EOF handling, automatic refresh, cross-platform/device validation and independent review of the full composition.

    Full candidate and implementation gates

    Account-trust protocol candidate for review

    This proposal combines the agreed policy with the local prototype evidence. It is a design candidate, not a production implementation or security approval. The native probes and signed Python reference model are separate components. Integration, specialist review and release validation remain required.

    Account anchor and authority

    The first client creating a new account generates its own fresh identity and a signed genesis record. The account anchor is a hash of the genesis content, independent of randomized signature bytes. The founder pins it locally. An additional client's first genuine anchor comes from its human-approved, PAKE-authenticated existing endpoint; relay login cannot establish or replace that trust. Removing the founding client leaves the public anchor and previously accepted history intact.

    One enrolled server has the account's ordering role. Initial designation is authenticated by the founding client during first-server setup; on Mac the normal choice is its automatically installed local server. The prototype supplies this designation as a fixture. Subsequent role changes require an ordered transfer naming the new server key, configuration epoch and exact preceding checkpoint, with old/new authority signatures. A transfer is planned management while the current authority is reachable; no automatic promotion, quorum or permanent-loss replacement is required.

    All approved clients and enrolled servers may submit signed account-management requests. The ordering server checks current authorization, serializes changes, persists the complete commit before acknowledging it and signs a receipt containing account/configuration, sequence, preceding hash and request hash. Stable request IDs make retries return the same commit. A removed issuer cannot append a later operation. The earlier rule applying both mutual removals is superseded.

    The authority must be honest and keep its current key/history. Restoring an old journal with the same key can create a valid fork; the native negative control demonstrates this. Clients retain checkpoints, reject rollback/conflicting extensions and halt affected account-state acceptance when a fork is detected. This does not establish global freshness or protect a fresh client supplied an entirely stale history. Relay withholding still permits the agreed unbounded revocation delay.

    Endpoint keys and approval

    Each endpoint owns its private identity keys. A signed admission manifest binds the personal account, endpoint identity, client/server role, TLS authentication key and HPKE agreement key with explicit purposes. Use one endpoint Ed25519 key for typed identity signatures and TLS authentication, and one P-256 HPKE key explicitly authorized for both recipient and authenticated-sender operations. The native holder-delegation path exercises both HPKE purposes with one key. Sender/receiver manifest association is not integrated across all probes yet. No private device identity is shared account-wide.

    Admission must prove possession of both private keys and reject reuse of known endpoint/role keys, including revoked-key tombstones. An encrypted nonce challenge bound to the signed enrollment request can establish HPKE-key possession. The prototype generates real key pairs and exercises their cryptographic operations, but that challenge/uniqueness registry is a required implementation gate, not a completed admission check.

    An additional client needs passkey sign-in and explicit approval from a trusted client or enrolled server. The new endpoint generates a secret code and a separate public rendezvous ID. Only the rendezvous ID and PAKE messages go through the relay. The approver receives the code from the user; a server approval command reads it locally without placing the secret in command arguments or relay lookup fields.

    Use the maintained BoringSSL SPAKE2 implementation as the prototype candidate, with its documented draft-02 variant. Do not describe it as RFC 9382 interoperability. Bind account/approver identity, request nonce, endpoint role and purpose keys into the confirmed transcript. Proposed code format is eight random decimal digits, paired with a public random rendezvous identifier. Requests expire after five minutes; each endpoint enforces at most five failed attempts and one successful completion. Restarting a request generates a new secret. The native probe currently demonstrates the full request gate on the Rust approver; the Swift primitive consumes one exchange per process. The complete client request lifecycle remains implementation work.

    After PAKE key confirmation authenticates the peer key binding, establish a pinned mutual TLS 1.3 approval channel and deliver genesis/checkpoints, the signed admission and directory-key envelopes over that channel. Use established TLS record encryption for these private payloads; do not add a bespoke PAKE-derived encryption protocol. The current PAKE and TLS probes demonstrate the primitives separately, not this entire approval-channel composition.

    Approval can complete while other account servers are offline. The approver signs the new endpoint's manifest and verifies subject key possession. A returning server checks that evidence against its verified account history without another manual approval. A completed signed admission does not inherit the pending request's five-minute expiry; it remains valid while its authority is accepted. Locally accepted admissions can operate from cached verified trust; reconciliation can still require fresh approval when an admission from a removed authority cannot be established before the ordered removal. A disconnected witness's unordered acceptance does not override removal. Already finalized admissions survive their approver's ordinary removal.

    Deployment enrollment

    Keep generic single-use invitations and reusable delegation distinct. A generic invitation has one trusted online issuer, an independently expiring/revocable ID and a high-entropy bearer secret. Default that issuer to the ordering server's existing endpoint key; another trusted issuer would need explicit registration. The subject generates its own keys and signs the enrollment request. The issuer checks the exact message purpose/field schema, scope and current validity, atomically allocates the invitation to that request, signs and persists the allocation before returning it. It is not an arbitrary signing service. A different subject cannot redeem it again. A trusted issuer's already verified winning allocation is retained on retry; the invite's later expiry does not remove that server.

    Reusable deployment credentials are account-owned role credentials, registered with independently managed expiry/revocation and server-enrollment-only scope. They have their own delegated signing and envelope keys, rather than cloning a server identity. A provisioned instance generates fresh endpoint keys and presents proof of possession; the delegation authorizes that specific server manifest. It cannot directly approve a client or revoke endpoints. An enrolled server gains the normal server authority already agreed, so a deployment credential remains sensitive account authority.

    Credential issuance/registration uses the ordering server in this candidate. Once issued, reusable deployment enrollment can run without another endpoint online. The credential holder can decrypt prepared directory-content-key envelopes and rewrap a key to the new instance's own recipient key. The native directory probe demonstrates this rewrapping after the original sender process exits. Import/provisioning of the credential secret and validation of the whole admission/envelope chain are not integrated yet.

    Removing a credential's creator does not revoke an already registered account-owned credential. A removed or compromised device may have copied credential secrets, so compromise cleanup must explicitly revoke exposed credentials and review affected approvals; ordinary removal does not claim to complete that cleanup. Credential expiry/revocation does not remove independently verified enrolled servers; their own keys remain members.

    First-time validation uses the receiving trusted endpoint's current clock, not the credential holder's claimed issuance time. A previously unseen enrollment first presented after expiry/revocation needs a fresh credential or current trusted-endpoint approval. When an already authorized independent endpoint verifies a valid delegation, it issues the normal server-admission certificate then, in a live exchange with the new server for its subject proof. The same already-issued certificate can be forwarded later while that issuer remains accepted; no new automatic post-expiry endorsement is created. A credential tag on that admission is an audit label, not proof of issuance time; the current member's admission authority is what makes the certificate valid. A subject or another endpoint derived only from the same unseen delegation cannot supply independent authority for its own backdating. An unrecorded certificate from a removed issuer needs fresh approval. This accepted late-unseen exception can affect a legitimate offline enrollment. Local server-owned sessions remain intact.

    Private account state and key distribution

    Store private directory/workspace content and signed account-state material as encrypted payloads at the relay. Keep server names, routes and private content inside encryption; operational routing metadata remains subject to the agreed telemetry policy. Sign plaintext records before encryption so possession of a content key does not confer membership or record-authoring authority.

    Use a fresh symmetric content key for each published directory snapshot/batch, with authenticated HPKE envelopes for the approved endpoint recipients and active deployment-role recipients. Bind account, record identity/version, verified membership checkpoint, recipient purpose key and sender purpose key into authenticated context. The prototype demonstrates CryptoKit-to-BoringSSL authenticated HPKE and AES-256-GCM, with fixture context/recipient selection. Full record/version handling and signed membership-driven recipient filtering remain implementation work.

    After removal or credential revocation/expiry, publishers that know the change stop new envelopes to that recipient and encrypt subsequent/current snapshots with fresh keys for remaining recipients. Recognized servers keep receiving envelopes under their own identities after their original enrollment credential expires. This avoids a shared long-lived content key acting as membership authority. Existing copied keys and retained ciphertext remain readable. HPKE storage envelopes do not provide forward secrecy against later recipient-key compromise.

    Publishers use verified membership and known revocations; stale/offline publishers cannot enforce unseen changes. Local/direct access has no automatic offline trust expiry. Reconnection retrieves and checks available updates, enforces valid learned removals and preserves tombstones/checkpoints. A removed identity is not silently re-enrolled. Suspected identity compromise requires revocation and explicit admission of fresh keys; ordinary key continuity needs authenticated old/new key bindings.

    Session channels and refresh

    Use mutual TLS 1.3 inside the opaque relay tunnel and on direct paths, authenticating account-approved endpoint keys rather than public hostname certificates alone. Disable early data and session resumption for the initial implementation; fresh connections perform a fresh authenticated exchange. Recheck membership on attachment/reconnection and disconnect a known-revoked client while preserving the server's processes.

    Proposed initial refresh defaults are a requested TLS KeyUpdate after ten minutes or 64 MiB in either direction, and a fresh authenticated connection after one hour or 1 GiB, whichever comes first. These are engineering defaults proposed for implementation, not measured production budgets. Keep the old authorized channel until replacement and attachment are ready, using the agreed session control/stream continuity contract. Automatic scheduling and seamless product handover remain implementation work.

    A TLS KeyUpdate does not repair exposure of the current traffic secret by itself. A fresh authenticated exchange can restore confidentiality after temporary traffic-state exposure if identity keys remain safe. It cannot repair a stolen identity key. The prototype observes real KeyUpdate messages, rejects altered/replayed records and preserves a server-owned shell through fresh connections. It does not extract traffic keys or prove compromise recovery.

    Wire and implementation gates

    Use versioned, purpose-specific signed bodies and bounded framing. Fixed identity/operation fields use strict encodings; arbitrary private metadata stays in signed/encrypted payload bytes. Verify the exact signed bytes before interpreting them, reject ambiguous/duplicate fields and bind account/configuration/checkpoint context at every boundary. The local pipe formats are prototype interfaces, not a production wire specification.

    Implementation must integrate native Rust account state with Swift clients, authenticated key storage, durable checkpoint/tombstone replay, planned authority transfer, recursive offline admission, capability-secret provisioning, directory record/version validation, bounded network framing, alerts/close_notify/EOF, automatic refresh and the production session attachment protocol. Native Windows/Linux/iOS/iPadOS and real relay/direct transport validation remain required before release. Keep repeatable regression/performance workloads and obtain independent review of the complete composition before treating it as secure.
