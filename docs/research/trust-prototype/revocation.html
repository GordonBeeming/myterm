An approval arriving after removal

A surviving device needs to distinguish an earlier offline approval from a new approval forged by a removed server. A valid signature alone does not establish which happened first.

Decision walkthrough only. This page models evidence and proposed behavior; it performs no cryptography. The separate native Swift/Rust PAKE probe passed 18 checks on macOS ARM64. Membership, TLS and terminal continuity remain unvalidated.

    What can A establish?

    Witnessing is relative to each device's verified history. A witness that has not learned of B's removal may still accept B's forged approval. Indefinite offline trust leaves that delay unbounded. Once histories reconcile, the agreed rule requires fresh approval when acceptance cannot be proven to precede removal.

    Probe evidence and remaining scope

    The native probe tests matching secrets, wrong codes, changes to the account/key/role binding, replay, reflected confirmations, malformed messages, request expiry boundaries, five failed attempts and refusal to reuse a verified request. Both callers use a pinned BoringSSL C core, whose SPAKE2 API describes draft-02.

    Confirmation is peer-local. One endpoint can verify a peer while the other rejects or never receives the corresponding confirmation. No membership is granted by this probe. Request state is in memory; expiry boundary tests use an injected fixture clock.
