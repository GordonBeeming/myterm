MyTerm · historical conflicting-removal experiment

Two histories, the same signed removal

A removed endpoint still holds its signing key. If it can select an old account checkpoint, it can create a removal that looks concurrent with its own removal.

Historical native experiment: 7/7 signed-history checks passed. Both signing orders produced the same signed bytes with BoringSSL; CryptoKit verified them. This page displays the measured public evidence. Receiver acceptance and lockout are reasoned consequences of the policy, not executed membership behavior.

Signing order represented by this scenario

    Evidence held by A

    A knows its own removal of B and receives a B-signed removal of A. Both records name the same earlier checkpoint where A and B were members.

    Same authenticated content, no issuance-time proof

    The old checkpoint and B's signature prove the signed claim and B's identity. They do not prove whether B signed before or after A removed it. B controls its claimed parents and any timestamp it signs.
