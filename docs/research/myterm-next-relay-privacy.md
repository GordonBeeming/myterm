# Relay compromise and private metadata

Research for [Establish what a compromised relay could learn](https://github.com/GordonBeeming/myterm/issues/126), 7 November 2026 AEST. This is a code and primary-source investigation, not a penetration test. Candidate designs below have not been selected or implemented. Line references describe this checkout.

## Findings

The current relay cannot satisfy Gordon's objective. Its database contains readable account, device and host labels, plus their relationships. Its running process sees authenticated connections and routing. Existing application encryption protects content under independently pinned peer keys; it does not conceal the connection graph. These are confirmed properties of the implementation, not evidence of an exploited vulnerability.

An encrypted account directory and endpoint-authorized enrollment can protect readable directory content against both database theft and a malicious relay. They cannot, by themselves, prevent that relay from discovering IP addresses, active routes, traffic patterns or persistent identifiers. No decision has been made to accept those residuals. The stronger requirement of no discoverable personal data remains open.

## Separate the attackers

| Attacker | Material available | Consequence |
| --- | --- | --- |
| Database copy | SQLite records, potentially WAL and backups | Reads current plaintext labels and relationships. Encrypted payload confidentiality depends on endpoint keys remaining secret. Certain retained token values can authorize relay access, as detailed below. |
| Running malicious relay | Requests, bearer tokens, memory, sockets, timing, routing and responses; ability to ignore authorization rules | Can collect metadata, lie about discovery, suppress updates, replay records or deny service. Pinned endpoint keys still constrain content forgery and decryption. |
| Relay plus compromised endpoint or provisioning authority | Endpoint secrets or admission authority in addition to relay access | Outside a relay-only guarantee. An authorized session server necessarily sees workspace data it operates on; encryption cannot protect that data from its own compromised process. |

The redesigned server owns workspace files and sessions, per the [agreed map](https://github.com/GordonBeeming/myterm/issues/125). Directory encryption therefore protects discovery and trust records; it does not relocate or back up workspace data.

### Token retry storage has a specific database-theft consequence

Tokens normally use random bytes and SHA-256 lookup hashes: [store.go:219](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L219). Refresh rotation deliberately stores the new raw access and refresh tokens to answer a lost-response retry: [store.go:646](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L646). The default retry grace is 60 seconds: [config.go:25](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/config/config.go#L25). Cleanup nulls these values after the grace: [store.go:186](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L186).

A stolen snapshot containing those raw values can be used against a reachable honest relay if the access token still has a row, is unexpired and its device is unrevoked, or if the refresh token is still current, unexpired and unrevoked. Those are the live validation conditions: [store.go:578](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L578), [store.go:627](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L627). The retry grace restricts answering an old refresh request; it does not make an already copied replacement token expire after 60 seconds. Later rotation or revocation can invalidate the copied pair. A retained backup can preserve the raw values after live cleanup, though usefulness still depends on live token state.

This is a confirmed bearer-token exposure condition under database theft, not a demonstrated exploit or a claim that every snapshot contains usable tokens. Relay authorization alone does not supply the pinned endpoint private keys needed to decrypt application traffic.

## Existing trust and its limits

Current pairing puts a host public key and a 32-byte secret in the ticket, limits lifetime to five minutes, consumes the secret before approval, and saves approved client keys: [PairingTicket.swift:4](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/PairingTicket.swift#L4), [PairingTicket.swift:177](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/PairingTicket.swift#L177), [PairingTicket.swift:210](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/PairingTicket.swift#L210). The client authenticates the response against the ticket's host key and saves that pin: [PairingCoordinator.swift:86](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Companion/Services/PairingCoordinator.swift#L86). This relies on receiving the genuine ticket through a trusted path.

Application channels use authenticated HPKE with pinned peers, binding comparison and ordered sequence checks: [AuthenticatedChannel.swift:197](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/AuthenticatedChannel.swift#L197). The client handshake uses its saved host key and validates the host response before creating the runtime channel: [CompanionHostConnection.swift:328](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Companion/Services/CompanionHostConnection.swift#L328). These checks support integrity against relay substitution and same-channel replay; a full handshake/reconnect audit was not performed.

HPKE itself supplies neither general replay protection nor plaintext-length hiding, and recipient private-key compromise can expose recorded ciphertexts. Its sender-authenticated mode does not turn an unverified directory key into a trusted identity. These are protocol limits, distinct from a relay-only breach. [RFC 9180, sections 9.1 and 9.7](https://www.rfc-editor.org/rfc/rfc9180.html#section-9.1).

Current discovery returns host names, public keys and online state from relay records: [server.go:515](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/httpapi/server.go#L515). Host keys are mutable in the database: [store.go:840](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L840). This does not establish an existing pin-bypass bug. It establishes why redesigning automatic trust around relay-returned keys would be unsafe.

Passkey authentication currently authenticates to the relay, whose process performs the checks: [auth.go:258](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/auth/auth.go#L258). A malicious verifier can bypass its own checks. Ordinary WebAuthn assertions do not supply a shared account decryption key. The optional PRF extension can support client encryption, but requires support checks and keeping results out of server submissions; WebAuthn warns that `toJSON()` includes those results. A compromised relay-hosted page would also control its JavaScript. [WebAuthn Level 3, PRF extension](https://www.w3.org/TR/webauthn-3/#prf-extension). No PRF-based design is selected here.

## Candidate protections requiring a decision

These are design requirements and options inferred from the threat model, not an approved architecture.

1. Encrypt directory labels, endpoints, membership and sensitive public-key associations on trusted endpoints. Keep private decryption keys outside relay control. A relay-held KMS key protects some storage-loss cases, but gives a compromised authorized relay the same decrypt permission. Decide who can decrypt the directory and whether each server needs the full directory.
2. Establish an account trust authority independently of relay login. Possibilities include an account signing authority held by approved endpoints, or a narrower delegation chain. Give admission certificates explicit account binding, subject key, role, scope, expiry and version. A login token must not automatically authorize a new decryption recipient. Decide authority ownership, delegation and whether an admitted server can admit others; none follows automatically from choosing account-wide encryption.
3. Bootstrap new clients through an existing trusted endpoint or another independently authenticated root. Persist the root and reject relay-supplied replacements. A fresh installation that obtains every trust anchor from a malicious relay has no independent basis to reject the attacker's account universe. Recovery must not silently reset that anchor.
4. For unattended servers, deliver a scoped, expiring enrollment authorization through trusted provisioning, bind it to the intended server key or require independent approval, and enforce use at trusted endpoints. A one-time flag enforced only by the compromised relay is insufficient. A clonable bearer invitation in a VM image grants every copy the same authority unless issuance binds each instance. The Azure scale-set validation must exercise that case.
5. Authenticate directory records and membership changes, retain monotonic versions, and define stale/offline behavior. Encryption alone does not prevent replay of an older valid directory. Trusted peers can retain checkpoints; a fresh device also needs a trustworthy current checkpoint. A relay can withhold the newest revocation, so the design must choose bounded freshness with refusal after expiry, or acknowledge a stale authorization window.
6. Keep session authorization and cryptographic revocation at session servers. Relay token revocation helps an honest relay only. Remove revoked recipients from future key distribution, rotate affected secrets where required, and define how every server learns the change. Revocation cannot erase plaintext or keys already copied by an endpoint. Current local peer removal and relay-device revocation are separate operations: [PairingTicket.swift:260](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/PairingTicket.swift#L260), [server.go:344](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/httpapi/server.go#L344).

Key transparency can help detect a directory presenting inconsistent key histories, with witnesses and monitoring. It introduces operational and privacy questions of its own and does not automatically establish legitimate admission. Signal's first-party description explicitly distinguishes consistent logs from accurate entries and describes eventual detection through monitoring. [Signal's automatic key verification design](https://signal.org/blog/automatic-key-verification/).

### Metadata remains a separate design problem

| Candidate | What it can reduce | Residual or cost to decide |
| --- | --- | --- |
| Encrypted directory with current account-authenticated relay | Readable labels and endpoints at rest | Relay still joins account/device/host activity and knows active routes and IPs |
| Opaque, rotating routing capabilities with fewer outer identifiers | Persistent application identifiers and database joins | Relay sees which live sockets exchange traffic; rotation can be linked through timing and simultaneous use |
| Independent ingress and routing services | Separates source IP visibility from account/routing knowledge if operators do not collude | Extra operators, latency and operational assumptions; stable credentials can reintroduce linkage |
| Anonymity network, padding and cover traffic | Can reduce address and traffic-pattern disclosure | Bandwidth, latency and mobile battery costs; no guarantee against a sufficiently capable correlating observer |

Oblivious HTTP separates relay and gateway knowledge and discusses timing/size correlation and padding. It addresses individual HTTP exchanges; applying that separation to MyTerm's persistent terminal tunnels requires additional protocol work. It is not a drop-in WebSocket solution. [RFC 9458, applicability and security considerations](https://www.rfc-editor.org/rfc/rfc9458.html#section-2.1). Tor also explicitly excludes protection against an observer correlating traffic at both ends. [Tor's stated remaining attacks](https://support.torproject.org/about-tor/security/attacks-on-onion-routing/).

For this architecture, a single compromised process forwarding both sides observes the active communication relationship even if all names and directory records are encrypted. Preventing that observation requires changing what any one compromised service sees. None of the options above has been approved as satisfying Gordon's no-discoverable-personal-data requirement. The next decision must name the observers and collusion assumptions, the identifiers they may learn, and the evidence required to demonstrate the claim.

## Recovery without assuming workspace loss

If a phone is lost but an authorized server and admission authority survive, a candidate design can re-enroll a replacement and rediscover that server. Workspace files remain on that server. If all directory-decryption/admission material is lost, workspace files can still exist while automatic discovery and proof of account membership fail. Local administrative access might allow explicitly rebuilding trust, depending on the chosen design. If the only workspace disk is lost, a directory recovery key does not restore its files.

A recovery key could preserve directory decryption or admission authority after loss of the normal holders. Its actual usefulness depends on which authority it recovers; it creates another sensitive capability to protect. Existing relay credential recovery deletes credentials and revokes relay devices, but does not demonstrate recovery of endpoint encryption authority: [store.go:314](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Services/relay/internal/store/store.go#L314). No recovery key, hierarchy, or recovery policy has been selected.

## Evidence needed after decisions

Use synthetic personal labels and capture a relay database, WAL, logs and traffic. Verify the stated attacker cannot read directory/workspace content or discover the specifically prohibited identifiers. Test substituted roots and server keys, forged enrollment, cloned provisioning invitations, replayed directory versions, rollback across reinstall, delayed revocations, reconnect replay and loss of all authority holders. Record the IP, route, length and timing observations that remain possible. These are proposed acceptance cases; no code or infrastructure changes or security tests were run for this research.
