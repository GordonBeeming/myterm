# Rust terminal state options

Research checked 7 November 2026 AEST. Scope: a Rust MyTerm server on native macOS, Linux and Windows, retaining SwiftTerm in native MyTerm clients. This is source review; neither replacement engine was built or measured here. Upstream links follow moving branches and must be pinned before a prototype.

## Recommendation

Evaluate `wezterm-term` first for server terminal state. Its library explicitly separates emulation from the GUI and PTY, accepts output bytes, and includes screen cells, scrollback and image support. This matches the proposed server boundary without a Swift helper. [Library overview](https://github.com/wezterm/wezterm/blob/main/term/src/lib.rs)

Keep `alacritty_terminal` as a text-terminal comparison candidate. It is a reusable emulator library with Unix and Windows dependencies, but its graphics gap makes it a weaker starting point for preserving MyTerm's existing image behavior. [Crate manifest](https://github.com/alacritty/alacritty/blob/master/alacritty_terminal/Cargo.toml), [open upstream Sixel request](https://github.com/alacritty/alacritty/issues/910)

The existing [MyTerm experiment](myterm-native-adapter-comparison.md) demonstrated portable Rust PTY adapters, and separately found failures when rebuilding `vt100` from `state_formatted`: partial UTF-8, CSI and OSC continuation and alternate-screen reconstruction. It did not demonstrate graphics fidelity. Those results concern that engine and reconstruction method; they do not eliminate other Rust engines or persistent parsing.

## Query response ownership

WezTerm's supplied writer carries keyboard/mouse input and terminal answerbacks to the program. Alacritty sends `PtyWrite` events and asks its embedder for colors, clipboard content and text-area size through callbacks. Both provide mechanisms for server-owned responses. [WezTerm constructor](https://github.com/wezterm/wezterm/blob/main/term/src/terminal.rs), [Alacritty events](https://github.com/alacritty/alacritty/blob/master/alacritty_terminal/src/event.rs)

Design inference: MyTerm should make one server authority responsible for replies and authoritative geometry even with zero viewers. SwiftTerm clients receiving raw output must suppress application-bound automatic replies, or the server must filter them through a defined response policy. Otherwise server and clients can answer the same query differently. Clipboard and other client-dependent requests need an explicit policy. On recovery or client replay, historical queries must not inject their answers into the live child again. Existing Windows startup handling remains a separate PTY requirement documented in the [adapter experiment](myterm-native-adapter-comparison.md).

## State lifetime and reconnect options

The source findings above support these design options; none has been validated for MyTerm with either candidate:

1. Keep a Rust worker alive per terminal session, retaining the parser, both screens and graphics state across client disconnects. A server coordinator can reconnect to that worker. This avoids serializing the emulator during normal detach/attach, but preserving the worker alone does not initialize a fresh SwiftTerm client.
2. Replay the complete ordered output and resize history into a fresh client or server emulator. Include initial geometry/configuration and relevant configuration changes. Suppress replayed side effects and query writes, then atomically hand off at a sequence number to live output. Retained bytes without resize ordering are insufficient. Storage and replay time grow unless a verified compaction boundary exists; an arbitrary ring-buffer suffix cannot reconstruct prior modes, images or partial parser input. A restarted emulator cannot restore a lost child process or PTY by replay alone.
3. Add a versioned full checkpoint to an engine fork, then store a checkpoint plus subsequent ordered events. It must cover partial parser state, both screens, pending wrap, saved cursor/modes, scrollback and graphics IDs/payloads/placements, with callbacks and writer rebound on import. This is substantial unimplemented work. A Rust checkpoint would also require a defined translation into SwiftTerm's client state; it cannot be imported as SwiftTerm's existing binary format by assumption.

A reconnect display export and a resumable parser checkpoint have different requirements. Repainting cells can initialize a view while still losing hidden modes, pending escape bytes or image references needed by later output. Neither candidate's supporting serde features establish a portable bounded reconnect format.

## Reuse and verification boundary

`wezterm-term` declares MIT and depends on several WezTerm workspace crates; adopting it requires pinning a compatible repository revision or maintaining a vendored subtree. Its library does not require adopting the GUI. The repository's MIT text requires retaining its notice; bundled fonts have separate notices. Inspect the actual transitive dependency set instead of copying distribution assets unnecessarily. [Crate manifest](https://github.com/wezterm/wezterm/blob/main/term/Cargo.toml), [license](https://github.com/wezterm/wezterm/blob/main/LICENSE.md)

`alacritty_terminal` declares Apache-2.0. Reuse the library with its applicable license/notice material and inspect transitive licenses; upstream product availability does not establish the licensing or build requirements of a particular MyTerm package. [Crate manifest](https://github.com/alacritty/alacritty/blob/master/alacritty_terminal/Cargo.toml), [upstream license](https://github.com/alacritty/alacritty/blob/master/LICENSE-APACHE)

The next experiment should pin WezTerm and feed the existing traces continuously, including every relevant split boundary. Compare query bytes and Unicode/cursor behavior, verify retained image pixels and placement/deletion, and test resize with both buffers. Run the headless engine plus the already-tested PTY adapter natively on all target hosts. Separately prove fresh SwiftTerm client initialization and replay-to-live ordering. Crash recovery, dependency/package size, image resource limits and any bounded checkpoint remain open until measured.
