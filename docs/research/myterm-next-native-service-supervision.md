# Native server startup and service supervision

Research date: 9 November 2026, AEST. Supports [Establish native server startup and service supervision](https://github.com/GordonBeeming/myterm/issues/151). This records source research rather than native service validation. The investigation did not install/register a service, change startup configuration, access credentials or deploy infrastructure. The acceptance probes below remain unrun. Subsequent product choices are recorded in [Choose native startup modes and unattended access guarantees](https://github.com/GordonBeeming/myterm/issues/167#issuecomment-6725509143); the recommendations and questions below preserve the research context.

## Findings and practical defaults

Native supervision can keep one Rust process per MyTerm server instance independent of the client UI on all three platforms. The important choice is the server's operating-system identity and login lifetime. A background process is not necessarily a boot service, and a running service does not prove that its files, keys or network are available.

| Platform | Practical candidate | What needs an explicit product/setup choice |
| --- | --- | --- |
| Personal Mac | A launch agent running as the owner, registered through Service Management, is the simplest candidate for automatic local startup at user login. It requires no running MyTerm client after registration. | It ends at logout. If logged-out phone access is required, investigate a launch daemon explicitly configured to run as the owner, with separate admin approval and a daemon-compatible key store. Do not silently downgrade the requirement to login-only operation. |
| Linux with systemd | A persistent user service enabled for `default.target`, with user lingering enabled for unattended operation. | Lingering and boot-readable home/key storage must be provisioned. A system unit with explicit `User=` is an alternative for managed deployments; it needs administrator installation but need not execute as root. |
| Native Windows | An auto-start SCM service using an explicitly selected non-administrator account, with the Rust executable implementing the service protocol itself. | Administrator installation, service-logon rights, secure account-credential provisioning and password-change handling are separate setup work. A user-logon scheduled task is a lower-friction alternative only if login-scoped availability is acceptable. |

These are recommendations for evaluation, not decisions made for Gordon. The factual lifecycle basis is [Apple launchd startup](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [systemd lingering](https://www.freedesktop.org/software/systemd/man/247/loginctl.html), [systemd execution identity](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml), [Windows auto-start](https://learn.microsoft.com/en-us/windows/win32/services/automatically-starting-services) and [service accounts](https://learn.microsoft.com/en-us/windows/win32/services/service-user-accounts).

## Repository constraints and evidence

- The [runtime resolution](https://github.com/GordonBeeming/myterm/issues/130#issuecomment-6707589863) selects one Rust server process per instance with internal terminal management. Shells and their programs remain ordinary child processes; there are no per-terminal MyTerm workers. Client quit/restart preserves live sessions. Actual server replacement, crash and reboot need not preserve them. Routine replacement defers while sessions remain active unless the user chooses to end them.
- The [workspace amendment](https://github.com/GordonBeeming/myterm/issues/130#issuecomment-6707945553) assigns shared layout to the account and terminal/browser runtime resources to each server. Supervision must not reintroduce a single machine-wide server identity.
- The [connection resolution](https://github.com/GordonBeeming/myterm/issues/133#issuecomment-6708378808) requires trusted automatic local setup without an account, local access by default, separate direct/relay opt-ins, and no relay connection, polling or retries while relay access is disabled. Native startup is not authorization to enroll or contact a relay.
- Existing [`SessionHostInstallation.swift`](../../Sources/MyTermPlatform/SessionHostInstallation.swift) installs stable helper copies; [`SessionHostServerAuthentication.swift`](../../Sources/MyTermContinuity/SessionHostServerAuthentication.swift) establishes an authenticated local helper boundary. They are useful migration evidence, not a portable service implementation. See the earlier [native-server investigation](myterm-next-native-server.md).
- [`SecureStorage.swift`](../../Packages/MyTermRemote/Sources/MyTermRemote/SecureStorage.swift) currently distinguishes terminal identity and notification-extension accessibility, with a noninteractive failure policy available. Its Apple client behavior does not establish that a Rust daemon can use the same store before login or after logout.
- Existing recovery in [`AgentSessionRecovery.swift`](../../Sources/MyTermCore/AgentSessionRecovery.swift) and [`AppModel.swift`](../../Sources/MyTerm/Models/AppModel.swift) distinguishes reattachment from a new shell using a saved agent resume command. Preserve the supported saved-directory/settings checks; do not label this arbitrary shell/process restoration.

## macOS

### Installation, identity and lifecycle

launch agents execute while their user is logged in; logout sends them `SIGTERM`. System launch daemons have a system lifetime. Apple's `UserName` plist key chooses the execution user when the supervising launchd is root: system supervision does not require a root MyTerm runtime. The launchd manual also defines separate job labels, explicit executable arguments, working directories and environment entries. [Apple startup guide](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [Apple launchd.plist source](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5).

On macOS 13+, `SMAppService` controls helpers bundled with an app and replaces manual installation of agent/daemon plists for that packaging route. Registering an agent bootstraps it immediately and at subsequent logins. Registering a daemon waits for admin approval before bootstrap, then bootstraps at subsequent boots. Registration status and denial must be surfaced during setup rather than reported as a running service. A one-time registration step is distinct from requiring the UI to launch after every reboot. [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice), [register()](https://developer.apple.com/documentation/servicemanagement/smappservice/register()).

Recommendation: evaluate the owner-identity daemon if the default personal-computer promise includes access after logout. Keep the Rust process unprivileged and use a narrowly scoped installer/registration operation for setup. Do not add a permanently running privileged coordinator. For login-scoped use, evaluate an owner launch agent. The selected packaging must also cover installation that has not yet opened the client; app-bundle registration alone is not evidence of that workflow.

FileVault requires credentials during boot and protects the data volume before unlock. Apple silicon on macOS 26+ additionally supports unlocking FileVault over SSH after restart when Remote Login is enabled and networking is available. This is a separate OS capability/setup path, not the MyTerm server running on a locked volume. [FileVault encryption](https://support.apple.com/en-gb/guide/security/sec4c6dc1b6e/web), [Managing FileVault](https://support.apple.com/en-gb/guide/security/sec8447f5049/web).

Inference: a daemon can cover a booted, disk-unlocked Mac sitting at its login window, subject to key/file availability. It cannot bypass FileVault. Do not promise unattended cold-boot phone access merely because a daemon is installed, or silently enable Remote Login, automatic login or change disk protection. Disk unlock, interactive login, screen lock and logout must be tested as distinct states; some ordinary flows combine them.

### Shell environment, files and keys

launchd supplies the configured working directory/environment, not a specification that the user's interactive shell setup has run. macOS separately requires consent for protected locations such as Desktop, Documents, Downloads, iCloud Drive and network volumes. [launchd.plist](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5), [Apple file-access controls](https://support.apple.com/guide/security/controlling-app-access-to-files-secddd1d86a6/web).

Recommendation: use an absolute server executable, explicit configuration/state paths and a minimal service environment. Resolve the owner's shell and home deliberately; define whether each terminal launches a login shell. Shell startup scripts, developer-tool PATH, SSH-agent sockets and credential helpers need their own probes. Do not source interactive startup scripts into the service manager or assume permissions granted to the Swift client automatically authorize the daemon or its children. A user-file permission error should identify the affected path and setup requirement.

macOS has file-based and data-protection keychains. A launchd daemon outside a user-login context must use the file-based implementation; setting its UID to the owner does not make it a user-login context. Data-protection access groups depend on executable entitlements/provisioning. [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains).

Unresolved adapter recommendation: prototype a daemon-compatible, noninteractive file-keychain access policy for the chosen owner identity. Explicitly select/search the intended store and verify its ACL and lock behavior. Alternatively evaluate an explicitly approved managed headless key source. Do not presume that the system keychain is readable by a non-root daemon, that login unlocks every store, or that iOS `AfterFirstUnlock` semantics apply to the classic Mac keychain. Never store the user's login/keychain password in a plist. Key unavailability needs a visible, retryable locked state; it must not regenerate an enrolled server's identity.

### Supervision, stop and packaging updates

`KeepAlive` can request continuous execution; rapid exits are throttled, and `ThrottleInterval` controls launch spacing. `SMAppService.unregister()` prevents further system launches. [launchd.plist](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5), [unregister()](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister()).

Recommendation: use native restart throttling plus application-level retry for unavailable keys/network. Distinguish invalid permanent configuration from temporary startup dependencies. A deliberate stop must unload/unregister or disable supervision before ending the process; merely exiting a kept-alive job is not a durable stop. Validate `launchctl print`, bootstrap/bootout and enable/disable behavior on each supported macOS version before documenting exact operational commands. The cited open-source manual is historical; it is not proof of modern launchctl domains or SMAppService behavior.

Stage updates outside the running executable's location until the server permits replacement. Bundled-helper replacement, app relocation/removal, code-signing identity and keychain ACL continuity need native probes. If SMAppService bundle updates cannot preserve an active server reliably, evaluate a separately installed versioned server payload; do not claim this packaging is selected or tested.

## Linux with systemd

### Installation and login independence

lingering starts a user's service manager at boot and keeps it after logout. User managers without lingering ordinarily follow login lifetime. User-unit search paths include user configuration directories; template units permit separately named instances. System units support explicit `User=`/`Group=`. [loginctl](https://www.freedesktop.org/software/systemd/man/247/loginctl.html), [systemd unit source](https://github.com/systemd/systemd/blob/main/man/systemd.unit.xml), [execution source](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml).

Recommended installation contract: install `myterm-server@.service` in an appropriate user-unit path, enable `myterm-server@<instance>.service` under the user manager's `default.target`, and provision `loginctl enable-linger <owner>` for unattended operation. Use `systemctl --user daemon-reload` and `enable --now` after installation. Linger authorization depends on local policy; report denial and provide an administrator setup path. Never put the server under `graphical-session.target` if logout survival is required. These commands describe a future installer; none were run. [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl), [user-manager lifetime source](https://github.com/systemd/systemd/blob/main/man/systemd-run.xml).

An administrator-installed system service template with fixed `User=` is a credible alternative where home directories or user managers are unsuitable. It should still launch the Rust server directly and use the intended owner's permissions. Units in an encrypted/unmounted home and their referenced binaries/state cannot be assumed available at boot. systemd documents mount dependencies for configured working/state directories, and separate encrypted-volume activation; these do not supply an absent decryption secret. [Execution/mount dependencies](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml), [crypttab](https://github.com/systemd/systemd/blob/main/man/crypttab.xml).

### Environment and private-key availability

service execution has configured environment and working-directory rules; `Environment=` is unsuitable for secrets. `LoadCredential=` provides a service credential delivery mechanism, and encrypted credential facilities have platform/version constraints. Secret Service runs in a user's login session and permits locked collections and unlock prompts. Lingering alone does not establish an unlocked desktop secret store. [systemd execution source](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml), [Secret Service specification](https://specifications.freedesktop.org/secret-service/latest-single/).

Recommendation: declare absolute binary/config/state locations and explicit shell settings. Do not rely on `.bashrc`, a desktop session's imported variables, mounted shares or `SSH_AUTH_SOCK` surviving logout. Probe PAM-dependent limits and shell behavior under the actual unit. For a boot service, select a provisioned headless key backend: credential delivery on supported systemd versions or an explicitly accepted owner-only key file with restrictive directory/file permissions and disk encryption. A plaintext owner-only file protects against other ordinary users, not offline disk access or compromise of that owner. Encrypting it with a wrapping key stored beside it adds no independent protection. This backend remains a security/product decision.

### Restart and deliberate stop

`Restart=on-failure`, `RestartSec=`, and unit start limits provide restart delay/rate control. Hitting a start limit can leave the unit failed until a later start/reset; it is not an infinite self-healing guarantee. An explicit systemctl stop does not trigger automatic restart. Default `KillMode=control-group` covers remaining child processes on stop. [Service restart](https://www.freedesktop.org/software/systemd/man/262/systemd.service.html), [start limits](https://freedesktop.org/software/systemd/man/devel/systemd.unit.html), [kill behavior source](https://github.com/systemd/systemd/blob/main/man/systemd.kill.xml).

Recommendation: start with `Type=exec` where supported, bounded restart rate and a short fixed delay; add readiness notification only if implemented. Retain control-group cleanup rather than letting shells escape to simulate survival. Use disable-and-stop for persistent opt-out, then remove the unit and reload for uninstall. Do not disable lingering indiscriminately on uninstall: other user services may rely on it. Do not copy generic `ProtectHome`/`PrivateDevices` hardening blindly; a terminal server needs the owner's files and PTYs. Confirm the minimum distribution/systemd version before selecting newer directives.

## Native Windows

### SCM service versus logon scheduling

SCM auto-start services start during system boot. Services execute under a configured account; SCM logs that account on and loads its profile. Installing services needs administrator access. The account password must remain valid, and the account needs service-logon permission. Service logon is not the user's interactive logon. [Auto-start](https://learn.microsoft.com/en-us/windows/win32/services/automatically-starting-services), [accounts](https://learn.microsoft.com/en-us/windows/win32/services/service-user-accounts), [SCM rights](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights), [account rights](https://learn.microsoft.com/en-us/windows/win32/ad/granting-logon-as-service-right-on-the-host-computer).

Recommendation: implement SCM service dispatch/control handling inside the same Rust executable; select a named non-administrator account, and provision rights/credentials through a protected installer path. Do not default to LocalSystem, LocalService or NetworkService: a different identity changes home, file permissions, key access and network credentials. Using the desktop owner's account is the most direct fit for that person's terminals, but passwordless/Microsoft-account/domain configurations require validation rather than a generic password prompt. A dedicated account avoids sharing the desktop identity but needs explicit grants to selected files and a distinct key store. Choosing between these is unresolved.

Scheduling alternative: `TASK_LOGON_INTERACTIVE_TOKEN` requires an existing interactive session. `TASK_LOGON_PASSWORD` requires the password during registration. S4U avoids storing a password but documents no access to network or encrypted files. Task settings independently govern restart attempts, execution time limits, battery stops and duplicate-instance policy. [Task logon types](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/taskschd/ne-taskschd-task_logon_type.md), [TaskSettings](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings).

Inference: a logon-triggered interactive task cannot meet before-login/logged-out availability. A password-backed noninteractive boot task is technically a separate option, but requires the same credential/setup scrutiny and explicit long-running settings. S4U must not be sold as a credential-free equivalent for the owner's full developer environment. Validate actual outbound socket, authenticated network-resource and encrypted-file behavior separately; the documentation's network restriction is not a measured MyTerm relay result.

### Files, environment and keys

a service has a different logon session, so it cannot use mapped drive letters established by the user's desktop session. Use authorized UNC paths for remote resources. Windows services run in session 0 and cannot assume an interactive desktop. [Redirected drives](https://learn.microsoft.com/en-us/windows/win32/services/services-and-redirected-drives), [interactive-service restrictions](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).

Recommendation: supply explicit state paths, working directory and shell configuration. Probe PowerShell profile/tool discovery and `cmd.exe` PATH as the service account; a loaded profile is not proof that interactive shell initialization, mapped drives or SSH agents exist. Native ConPTY creation and child cleanup must be exercised in the service context, not only a console test. No extra per-terminal MyTerm executable is needed for that adapter. [Microsoft pseudoconsole lifecycle](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session).

DPAPI normally binds decryption to the same user credentials and machine; machine scope permits any user on the machine to decrypt the protected blob. UI-forbidden mode supports noninteractive operations. [CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

Recommendation: evaluate user-scoped DPAPI under the actual service account, with ACL-protected storage and no prompts. Do not use machine scope to paper over an identity mismatch. Validate cold boot, password rotation/reset, locked desktop, logout, profile availability and a second account's denial. Keep SCM logon credentials separate from MyTerm identity/enrollment credentials. No private keys or passwords belong in service command lines, task XML, environment entries or logs.

### Recovery, stop and removal

SCM failure actions can restart with configured delays and reset periods; the final configured action repeats after the list is exhausted. The service must report lifecycle status and handle stop requests promptly. `DeleteService` marks a service for deletion until it stops and open handles close. [Failure actions](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actionsw), [control handler](https://learn.microsoft.com/en-us/windows/win32/services/service-control-handler-function), [DeleteService](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-deleteservice).

Recommendation: use staged restart delays and an eventual no-action state for a crash loop, with diagnostics and an explicit retry path. Never configure machine reboot as MyTerm failure recovery. Deliberate stop reports `SERVICE_STOPPED`; persistent opt-out changes startup policy as well. Uninstall stops/disables before deletion and verifies removal rather than treating deletion marking as completion. Give each instance its own service name and state paths, and quote the executable path correctly. Validate process-tree cleanup, potentially through a Job Object, rather than assume SCM owns every shell descendant. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

## Lock, sleep, network and updates

A locked screen is not logout. Agent/service lifetime and key accessibility are independent: a still-running process can retain a loaded identity key while a restarted process cannot reread it. Both cases need probes. A phone connection additionally requires an explicitly permitted direct or relay path; local-only default installation should remain unavailable remotely by design. [Apple lifecycle](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [connection policy](https://github.com/GordonBeeming/myterm/issues/133#issuecomment-6708378808).

Ordinary macOS sleep does not execute scheduled launchd jobs until wake; Linux supports suspend/hibernate states; Windows has multiple power states with different execution/network behavior. Native supervision is not a promise of continuous phone reachability during sleep. [Apple launchd schedule behavior](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5), [Linux power-state documentation](https://docs.kernel.org/admin-guide/pm/sleep-states.html), [Windows power states](https://learn.microsoft.com/en-us/windows/win32/power/system-power-states).

Recommendation: preserve ordinary power policy by default. On wake/network change, re-establish only enabled transports with bounded retry/jitter; do not treat sleep as relay opt-out or regenerate identity. An optional keep-awake policy, Wake-on-LAN or other remote-wake expectation needs a separate choice and hardware-specific validation. Windows BitLocker can also require preboot authentication, while Linux encrypted volume activation depends on provisioned keys; boot-service installation does not remove either gate. [BitLocker preboot authentication](https://learn.microsoft.com/en-us/windows/security/operating-system-security/data-protection/bitlocker/planning-guide), [crypttab](https://github.com/systemd/systemd/blob/main/man/crypttab.xml).

Proposed update contract, inferred from the runtime resolution: stage and verify a new version while the old process keeps running; ask that process for an atomic drain/update decision. Count active terminals even if no client is attached. Serialize new-session creation against entering the drain state so a stale zero-session check cannot kill a newly created terminal. Browser-runtime policy needs clarification. Replace only once quiescent or after explicit end-session consent; never use an ordinary package-manager restart hook to bypass this gate. Retain the previous payload until startup/readiness succeeds, and validate state-schema compatibility before promising rollback. [Runtime policy](https://github.com/GordonBeeming/myterm/issues/130#issuecomment-6707589863).

Each instance needs a stable local instance identifier, separate supervisor name, configuration/state/log/secret namespace, IPC endpoint and optional direct listener. Reject duplicate ownership of the same data directory before opening it for writes. Two instances under one UID are operationally separate, not protected from each other as separate security principals. Distinct OS identities and ACLs are needed for stronger isolation; no service naming scheme alone provides it. These are implementation recommendations consistent with the [multiple-instance model](../../GLOSSARY.md).

## Product choices to take back to Gordon

1. Does the default personal Mac promise include logged-out operation, or only logged-in/locked operation? The answer selects the agent/daemon lifetime and changes secure setup. Neither option implies bypassing disk unlock.
2. Which non-root owner and unattended key backend are acceptable for the daemon/VM cases? Is an owner-only disk-protected key file acceptable on Linux, or is a managed credential/hardware-backed route required? Which Windows account/credential modes must be supported?
3. What power behavior is promised: reconnect after ordinary wake, or an explicit opt-in to keep a host awake? No platform-wide remote-wake guarantee has been established.
4. What constitutes update-blocking activity beyond live terminals, including browser sessions? How should prolonged deferral be shown, and does a separate emergency-update policy exist? Routine updates already have a decided deferral rule.
5. What exact OS/distribution versions, installer formats and admin-denied experience are supported? Clarify retention of local state/identity during uninstall separately from account removal/revocation.

## Required native acceptance probes

Run these on supported native macOS, Linux and Windows hosts after implementation. Save OS/version/architecture, executable version/hash, actual identity, supervisor definition/status, PID/process tree, timings and redacted logs. Existing PTY adapter evidence does not establish any service lifecycle result. Record test timestamps in UTC files and present them in AEST.

| Probe | Concrete steps and required evidence |
| --- | --- |
| Build and clean install | Build the Rust server for each native target. Install/register through the proposed signed package/installer, including paths with spaces/Unicode. Check denied/cancelled admin approval, idempotent reinstall, actual unprivileged UID/SID, service status and diagnostics. No client process may be needed for continuing execution. |
| First startup without client launch | Install on a clean user/machine, complete only required setup, reboot and connect using the intended local access path without first launching the MyTerm UI. Capture the service PID/readiness before any client opens. Distinguish an installer registration requirement from a per-boot app requirement. |
| Local-first boundary | Install without an account and capture process-attributed DNS/network attempts and listeners across startup, crash retry and wake. Require authenticated same-machine access, no LAN scanning/direct listener by default and no relay attempts. Enable direct and relay independently; verify disabling relay immediately closes it and ends retries while local sessions continue. |
| Client-independent lifetime | Start a long-running terminal command with an observable PID/counter. Quit/restart the Mac client repeatedly and detach every client. Verify identical server/shell PID and continuing output. With remote access explicitly enabled, connect from the phone while the desktop client is absent. |
| Lock and logout matrix | Lock the desktop while the server runs, connect, then separately crash/restart the server while still locked and try again. Log out completely, including the final session, and repeat. Agent/login-task expected failure must be stated; the selected unattended mode must pass without UI/keychain prompts. Include multi-user/fast-switch cases and Windows noninteractive logon. |
| Cold boot and disk unlock | Test encrypted disk locked, disk unlocked but owner not interactively logged in, and owner logged in. Record whether files, keys, networking and server readiness are available independently. Test configured remote disk-unlock paths only with explicit setup. A blocked preboot disk is not a service crash. |
| Shell environment and files | From a service-owned terminal record sanitized PATH, home, working directory, shell mode, identity/groups and tool resolution. Exercise permitted project files plus denied files, macOS protected folders and external/network volumes; Windows UNC versus desktop mapped drive; Linux unmounted/encrypted home. Verify permission guidance and no elevation fallback. |
| Key storage | Generate distinct disposable instance keys and prove noninteractive sign/handshake before/after lock, logout, service restart and reboot. Deny another OS user. Exercise missing/locked/corrupt store, changed binary signing identity, password changes/reset and changed profile. Require preserved enrolled identity or explicit recovery, never silent replacement. |
| Crash and backoff | Kill only the Rust server; count restarts and intervals, verify startup-limit/no-action state and explicit recovery. Test unavailable key/network, invalid configuration and intentional clean exit separately. Repeated failures must not spin, flood logs or reboot the host. Lost shells may end; check no orphan process trees or false live-session claims. |
| Deliberate stop and uninstall | Stop the instance through its supported control path, wait beyond recovery delay and confirm no resurrection. Reboot to distinguish temporary stop from persistent disable. Uninstall one of two instances, verify no remaining launch registration/task/unit/service, and confirm the other instance plus unrelated linger users remain operational. Verify the chosen state/key retention policy. |
| Suspend and wake | Suspend/hibernate with live shells, wake onto same/different network, and reconnect over enabled paths. Record PID/state outcome and bounded retry. Test Windows supported power modes and Mac laptop lid behavior separately. Do not record sleep-time unreachability as successful always-online service. |
| Multiple instances | Start A/B concurrently with separate identity/state/endpoints and different transport settings. Stop/crash/update A; prove B stays running. Attempt duplicate instance ID, data directory and port; require safe refusal with useful diagnostics. Verify local IPC peer authentication and filesystem/pipe ACLs against another user. |
| Deferred update race | Keep a terminal active with all clients detached, stage an update and prove the old PID/binary continues. Race new-session creation against drain, then close the last session and apply. Test explicit end-session consent, restart failure, power loss during staging and compatible rollback. Reopen the client and verify supported agent recovery after deliberate server loss without claiming old processes survived. |

Implementation acceptance requires the native probes, including logged-out key access, service-owned ConPTY behavior, secure first installation and update continuity.
