# Native server implementation options

Research date: 7 November 2026, AEST. This note supports [Establish the native server implementation options](https://github.com/GordonBeeming/myterm/issues/127). It records source inspection and primary documentation research. No candidate was implemented, built or executed for this investigation; existing workflow definitions were inspected, and their latest run results were not fetched.

## Findings that affect the decision

All three approaches below are credible investigation candidates. Go offers continuity with the relay and straightforward separation from Apple frameworks. Swift preserves the most terminal and workspace code, with substantial Windows adapter work. Rust offers an existing Unix/ConPTY abstraction and terminal libraries, at the cost of another implementation language and a new client synchronization boundary. None has demonstrated MyTerm's complete native Windows workflow.

The current helper already owns a PTY, terminal emulator and retained history independently of a visible terminal view. It is useful architectural evidence. It is not the standalone workspace server required by the destination: remote routing and workspace commands still pass through the Mac application's model. The browser requirement also changes an explicit current policy that rejects private networks.

Keep runtime choice separate from terminal-engine choice. Replacing SwiftTerm with a Go or Rust emulator can save integration work on one side while creating compatibility work for the native Swift clients. A language-neutral cell/state protocol or a shared terminal core needs its own experiment before choosing the server language.

## Process boundaries worth comparing

Every option needs a server that owns workspace persistence, session identities, terminal authority, writer leases and enrolled-client admission. The Mac app becomes a client of that server, including its default local instance. Direct and outbound relay transports should feed the same authenticated command handling. Loopback access still requires authentication.

Two process layouts are viable design choices:

1. One server process owns all PTYs and emulator instances. This simplifies deployment and state access. A server crash or an upgrade that restarts it affects every session. Saving workspace JSON and terminal checkpoints does not restore running processes.
2. A server supervises persistent session workers. Each worker owns its PTY and terminal state; the server owns workspace authority and remote access. This extends the existing helper shape and can let workers survive a server restart. It adds authenticated worker IPC, version negotiation, stale-worker discovery and platform service policy work. Worker survival during service restart must be tested rather than assumed.

In either layout, closing the UI or losing a network connection must detach clients without closing PTY handles. Define separately what survives server crashes, service stop, logout, upgrade and machine reboot. Persisted terminal content cannot promise continuation of a process after reboot.

## Runtime and library options

| Option | Practical components | Advantages | Main work and uncertainties |
| --- | --- | --- | --- |
| Go server with native adapters | Go service and transport; `creack/pty` on Unix; a reviewed ConPTY binding on Windows; Go VT engine or separate shared terminal core | Uses a language already in the repository and keeps Apple clients native. A server executable can have a small operational surface. | Reimplement workspace rules or share them through a separately versioned boundary. Validate Go emulator parity, snapshot encoding, Windows process trees and native secret storage. Go alone provides no PTY or emulator semantics. |
| Portable Swift server | Extract workspace/core targets; retain SwiftTerm parser/checkpoints; conditional CryptoKit/Swift Crypto; replace `Network` and `Security`; Unix adapter plus ConPTY bridge | Maximum reuse of model behavior and existing parser/checkpoint tests. Same language can reduce accidental schema divergence. | Existing helper is Apple specific. Windows PTY implementation is absent. Confirm networking/TLS package support and crypto support for each Windows CPU before committing. Portable image handling still needs work. |
| Rust server | `portable-pty`; `vt100` or a separately evaluated richer terminal engine; Rust networking/crypto and OS storage adapters | Existing PTY abstraction explicitly selects Unix and Windows ConPTY implementations. Gives a plausible common process boundary. | New Rust build/release maintenance and workspace migration implementation. `vt100` screen reconstruction does not establish SwiftTerm graphics, keyboard or checkpoint parity. A Rust worker behind Go adds IPC and two server runtimes. |

For Go, [`creack/pty`'s Windows implementation](https://github.com/creack/pty/blob/master/start_windows.go) returns `ErrUnsupported`. A Windows adapter is therefore mandatory. [`UserExistsError/conpty`](https://github.com/UserExistsError/conpty) is a concrete Go binding candidate with process, stream and wait APIs; its README is evidence of an API, not evidence of production suitability. Compare its handle cleanup, cancellation and process creation against Microsoft's implementation guidance before adopting it.

For terminal state in Go, [`charmbracelet/x/vt`](https://pkg.go.dev/github.com/charmbracelet/x/vt) documents an emulator, screen cells, damage and bounded scrollback APIs. That makes it worth testing. It does not establish compatibility with this checkout's SwiftTerm checkpoints, Unicode widths, reflow or image support. Pin a reviewed release before comparing it; current documentation may move.

For Swift, official installers exist for [Windows](https://www.swift.org/install/windows/) and [Linux](https://www.swift.org/install/linux/ubuntu/). Windows installation depends on the [C++ toolchain and Windows SDK](https://www.swift.org/install/windows/manual/). These establish a native toolchain route without WSL. They do not port Apple frameworks. [SwiftNIO](https://github.com/apple/swift-nio/blob/main/README.md) is a networking candidate; verify the exact pinned modules and Windows execution paths, including TLS and WebSocket behavior, rather than assuming the umbrella's cross-platform description covers every dependency.

For Rust, [`portable-pty`](https://docs.rs/portable-pty/latest/portable_pty/) exposes spawning, resize and stream handles. Its [source](https://docs.rs/portable-pty/latest/src/portable_pty/lib.rs.html) selects `UnixPtySystem` on Unix and `ConPtySystem` on Windows. [`vt100`](https://docs.rs/vt100/latest/vt100/) parses bytes into screen state and can produce formatted contents/differences. These are separate PTY and emulator components. Neither automatically implements MyTerm's reconnect protocol or feature set.

A Go coordinator with a SwiftTerm worker remains a possible reuse strategy, but native Windows still needs the Swift adapters and toolchain. It does not remove the portability work. A common Rust terminal worker could serve either coordinator language, but deserves consideration only if its terminal behavior wins the compatibility experiment.

## PTY and terminal authority requirements

Unix PTYs require a controlling terminal, not merely redirected stdin/stdout. The Linux man-pages project's [`openpty`, `login_tty`, `forkpty` documentation](https://man7.org/linux/man-pages/man3/openpty.3.html) explains allocation and controlling-terminal setup. Test job control, foreground process groups, resize delivery, shell startup and stop behavior independently on macOS and Linux.

Windows ConPTY creates a native pseudoconsole and launches its child through extended process startup attributes. Microsoft documents [creation and lifecycle](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), including synchronous pipe I/O and separate servicing of the communication channels to avoid deadlocks. [`CreatePseudoConsole`](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole) emits UTF-8 text with VT sequences and documents minimum availability of Windows 10 version 1809 and Windows Server 2019. Product support versions still need a decision. Validate PowerShell and `cmd.exe`, Unicode paths/environment, control keys, resizing during output, process termination and final output draining on native Windows.

The server's authoritative emulator must keep processing output when no client is attached. It must answer application terminal queries exactly once. Current helper `send(source:data:)` delegates replies to the visible emulator while attached and answers them while detached. Multiple viewing clients require a new single-responder rule, preferably server owned, to avoid duplicate capability/cursor replies.

A checkpoint must restore parser state, modes, both buffers, cursor, history and supported graphics at a known stream position. A plain text screen dump loses behavior. Specify sequence/generation, checkpoint-to-delta ordering, history truncation, writer-controlled resize and bounded slow-reader behavior. Test CJK/emoji/combining characters, alternate screens, split escape sequences, hyperlinks, mouse modes, Kitty keyboard/graphics and Sixel against the feature set the release promises. Existing [`Tests/MyTermContinuityTests/PersistentTerminalImageTests.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Tests/MyTermContinuityTests/PersistentTerminalImageTests.swift) and SwiftTerm checkpoint tests supply useful fixtures; a different engine needs behavioral comparisons rather than copied JSON assertions.

## Crypto and private keys

Current [`AuthenticatedChannel.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/AuthenticatedChannel.swift) uses authenticated HPKE with `P256_SHA256_AES_GCM_256`, sender identity, encoded binding/AAD and ordered sequence checks. [`HelloHandshake.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/HelloHandshake.swift) binds pinned agreement and notification signing keys. Reuse these as interoperability cases if retaining those choices; the old protocol is not a product constraint.

[RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html) defines HPKE modes and suites. Matching primitive names alone does not prove compatibility: test public key serialization, Auth mode, `info`, AAD, ciphertext/tag layout, malformed keys and authentication failures in both directions. Add byte-level fixtures and replay/reconnect tests before mixing languages. Go's [CIRCL HPKE API](https://pkg.go.dev/github.com/cloudflare/circl/hpke) includes authenticated sender/receiver setup. Rust's [`hpke`](https://docs.rs/hpke/latest/hpke/) is an RFC 9180 candidate. Adoption still requires suite, maintenance and security review.

[Swift Crypto's current README](https://github.com/apple/swift-crypto) explicitly describes Linux and ARM64 Windows support. Do not infer Windows x86-64 support from the Swift installer architecture list. Confirm a pinned version, required HPKE APIs and native x86-64 build/run status, or identify an approved alternate crypto backend. That is an unresolved Swift option experiment, not a demonstrated impossibility.

Storage must match the server's service identity and unattended startup needs:

| OS | Candidate | Evidence and required check |
| --- | --- | --- |
| macOS | Keychain adapter | Existing [`SecureStorage.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/SecureStorage.swift) has `SecretStore`, accessibility choices and a fail-without-UI policy. Test restart while locked and after reboot under the actual launch identity. Existing interactive login behavior does not prove unattended access. |
| Windows | User-scoped DPAPI or reviewed credential/CNG adapter | Microsoft's [DPAPI guidance](https://learn.microsoft.com/en-us/windows/win32/SecCrypto/example-c-program-using-cryptprotectdata) binds default decryption to the same user and machine; machine scope broadens access. Verify service account/profile behavior and recovery before selecting scope. |
| Linux | Secret Service where deployed; explicit managed headless backend | The [Secret Service specification](https://specifications.freedesktop.org/secret-service/latest-single/) permits locked collections and interactive unlock prompts. Availability and unlocked state cannot be assumed on a VM startup path. Choose and test a provisioned key source; encrypted files still need a way to supply their wrapping key. |

Native storage does not settle account recovery, enrollment, revocation or relay metadata privacy. The server is trusted to decrypt what it needs; relay code must never receive plaintext private decryption keys. Keep account/key architecture and the requirement for no discoverable personal data open for the separate security decision. Changing server language cannot establish that objective.

## Proxy-only browsing

There is already a useful client-side shape. [`Companion/Views/RemoteBrowserView.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Companion/Views/RemoteBrowserView.swift) configures a local HTTP CONNECT or SOCKS5 endpoint for `WKWebsiteDataStore`, includes localhost matches and disables failover. [`BrowserTunnel.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Packages/MyTermRemote/Sources/MyTermRemote/BrowserTunnel.swift) defines logical stream open/data/ack/close messages and bounded chunks, but uses Apple's `Network` sockets. Preserve the native WebKit client while implementing portable server-side TCP streams.

The verified conflict is [`NativeBrowserDestinationPolicy.swift`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Sources/MyTerm/Companion/NativeBrowserDestinationPolicy.swift): it rejects loopback, private and local-interface addresses. [`CompanionHostModel.handleBrowserTunnel`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/Sources/MyTerm/Companion/CompanionHostModel.swift) calls it. The new server must deliberately authorize server-local/private destinations and resolve/dial them on the server. Simply enabling the current native mode will not satisfy the agreed requirement.

Prefer an authenticated byte tunnel feeding a local client proxy as the first architecture to investigate. This keeps original web origins, TLS and browser rendering at the client. An HTTP page-rewriting proxy creates additional origin, cookie and script rewriting obligations. In either case validate remote DNS, localhost routing, redirects, HTTP/WebSocket upgrades, cookies, authentication callbacks and no direct fallback with real WebKit traffic. OS/browser proxy exceptions require execution evidence. A local file needs an explicit server file-serving grant and containment policy; TCP proxying does not define `file://` semantics. Mac-rendered snapshots are outside the agreed browser direction.

## Service lifecycle and verification

On macOS, [launchd user agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html) are tied to a logged-in user. They can meet UI independence without establishing logged-out operation. On Linux, systemd's [`enable-linger`](https://www.freedesktop.org/software/systemd/man/latest/loginctl.html) can keep a user manager active after logout and start it at boot. On Windows, [services run without direct user interaction](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). Choose a service identity with the intended workspace permissions; running a shell as a broad system identity changes the trust boundary. Test each intended mode, including Azure VM scale-set startup enrollment, rather than extrapolating from a developer terminal.

Existing CI evidence is limited to definitions:

- [`.github/workflows/build.yml`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/.github/workflows/build.yml) defines macOS Swift build/tests and real bundle/helper verification on `xcode-27`.
- [`.github/workflows/companion.yml`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/.github/workflows/companion.yml) defines Mac remote-package tests, relay tests on Ubuntu, and Apple companion jobs. It provides no native Windows session server test.
- [`.github/workflows/relay-release.yml`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/.github/workflows/relay-release.yml) defines Go tests/race/vet on native Ubuntu x86-64 and ARM64 runners. [`script/package_relay.sh`](https://github.com/GordonBeeming/myterm/blob/9bfa0ea4867107e77fa8414d44b1b5331f593aa4/script/package_relay.sh) builds Linux relay Docker archives and smoke-tests matching native architecture. This covers the relay packaging path, not Linux PTY servers or Windows execution.

[GitHub's hosted-runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) provides native OS/architecture choices. Add native server jobs for every supported OS/CPU, pin the toolchain and record actual runtime evidence. Cross-compilation is a useful build check; it cannot verify ConPTY, service startup, Keychain/DPAPI access or process cleanup.

## Experiments needed before a runtime decision

These are proposed follow-up work, with no implementation performed here.

| Experiment | Evidence that would resolve it |
| --- | --- |
| Minimal native server slice in leading candidates | On macOS, Linux and Windows without WSL: spawn shell, stream input/output, resize, disconnect/reconnect and preserve final output. Record OS/CPU/toolchain and command results. |
| Terminal engine comparison | Replay identical byte/resize traces into existing SwiftTerm and candidates; compare cells, modes, retained history and reconnect behavior; report unsupported graphics/keyboard behavior explicitly. |
| Swift Windows dependency slice | Build and run extracted parser, crypto suite, sockets/TLS and ConPTY bridge on required Windows CPUs. Resolve the Swift Crypto x86-64 support question against the chosen version. |
| No-UI authority and writer leases | Quit the Mac UI, attach phone, change workspace, transfer control, reconnect two viewers and verify one accepted writer through direct and relay transports. |
| Private-site proxy | Native clients load server loopback and private DNS sites, HTTPS and WebSocket apps; capture server-side connections and verify no direct client fallback. Include cookie/auth flows and file-grant decisions. |
| Unattended enrollment/storage | Reboot and start under final service identity with no UI; exercise locked/unavailable store, revoked enrollment and expired credentials. Include actual VM scale-set startup. |
| Upgrade/crash boundary | Stop UI, kill server, restart service, upgrade coordinator/worker versions and reboot separately; report exactly which sessions and data survive. |
| Migration | Load representative existing workspace versions, preserve backups, split client selection from topology and verify identifiers/settings without silent loss. |

Go deserves the first deployment/adapter spike if reducing new server ecosystem work is the priority. Swift deserves the first extraction spike if terminal fidelity and existing model reuse dominate. Rust deserves the first terminal-worker spike if a common native PTY layer and terminal engine outweigh introducing a new language. Those are conditional recommendations. The native Windows slice and terminal compatibility results should inform Gordon's implementation choice; this research does not resolve that decision.
