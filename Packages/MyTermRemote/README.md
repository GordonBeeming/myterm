# MyTermRemote

`MyTermRemote` contains the shared native protocol for the MyTerm Mac host and iPhone companion. It has no dependency on `MyTermCore`. Workspace projections, command bodies, and terminal checkpoints cross this boundary as bounded `Data`; each app decodes those values into its own model types.

The package provides:

- HTTPS relay requests with ephemeral sessions, same-origin redirect checks, rotating refresh tokens, and Keychain storage
- a single-reader WebSocket actor with bounded event and write queues
- pinned P256 identities, authenticated HPKE application channels, and separate P256 notification signing keys
- QR pairing tickets, one-use Mac approval, typed outer packets, and a three-message hello handshake
- typed inner messages, checkpoint assembly, connection generations, controller leases, and push notification SDK types

## Identities

Keep these identifiers separate:

- `LocalDeviceIDStore` persists the app's pairing identity UUID. Fresh passkey login may return a different relay `device_id`, so that relay ID cannot identify a paired peer.
- `DeviceIdentityStore` persists the P256 key agreement private key used by pairing and terminal HPKE.
- `SigningIdentityStore` persists the P256 signing private key used for notification grants and signatures.
- `TokenStore` partitions relay tokens by canonical relay origin, relay `account_id`, and relay `device_id`.

Create `KeychainSecretStore` instances with `.terminalIdentity` for app-only identity and token material. The notification extension store needs its App Group access group and `.notificationExtension`, which maps to `AfterFirstUnlockThisDeviceOnly`.

`RelayHTTPClient.devices`, `revokeDevice`, and `disconnectPeer` expose relay management. A host can disconnect one client connection without revoking the phone's relay login or stable pairing identity.

## Pairing over the relay socket

The Mac calls `PairingRegistry.begin(...)` and displays `PairingTicket.qrURL()`. The QR contains the relay origin, host ID, pinned host agreement key, public ticket ID, 256-bit secret, and five-minute expiry. The relay never receives the secret.

After passkey login, the phone opens `RelayWebSocketClient` and sends a proposal:

```swift
let proposal = PairingProposal(
    ticketID: ticket.ticketID,
    secret: ticket.secret,
    clientDeviceID: localDeviceID,
    clientPublicKey: clientAgreementKey.publicKey.x963Representation,
    clientNotificationSigningPublicKey: clientSigningKey.publicKey.x963Representation,
    clientName: deviceName
)
let sealed = try PairingCrypto.sealProposal(proposal, ticket: ticket)
let packet = try RelayApplicationPacket.pairingProposal(sealed).encoded()
try await socket.send(destinationConnectionID: RelayFrame.broadcastDestination, payload: packet)
```

The unpaired Mac accepts only `.pairingProposal`. It opens the proposal with its private agreement key, passes it to `PairingRegistry.authorize`, and asks the user to approve. The registry consumes the local ticket before awaiting approval, so denial and abandoned approval cannot reuse the QR. After approval, the Mac sends `PairingCrypto.sealResponse(...)` inside `.pairingResponse` to the trusted source connection ID from `RelayTransportEvent.application`.

The phone opens the response with its agreement key and the host key pinned by the QR. Both apps persist the peer's stable local identity and public keys. Relay `peer` events still describe transport presence only.

## Authenticated hello

Create directional hello bindings with the stable relay `account_id`, `runtimeID: nil`, `purpose: .hello`, and an epoch generated by the phone for this connection attempt. The sender and recipient IDs are the stable local pairing IDs.

1. The phone creates `HelloHandshake.challenge(...)`. Its metadata has no runtime ID.
2. The Mac validates the encrypted challenge, then calls `HelloHandshake.response(...)`. It sends the response with its current runtime ID in `MessageMetadata`. The response echoes the phone challenge and contains a fresh host challenge plus `applicationEpoch`.
3. The phone validates the pinned host key and challenge echo, then sends `HelloHandshake.acknowledgement(...)` with the returned runtime ID. The Mac checks the host challenge response and pinned client key.

After the acknowledgement, construct new directional `ChannelBinding` values with `purpose: .application`, the returned runtime ID, and the host-generated `applicationEpoch`. Create a new `SecureRelayChannel` after every reconnect. Sequence gaps end that channel; input is never replayed.

## Inner protocol

`InnerMessage` encodes flat snake-case JSON with `version`, `kind`, the IDs in `MessageMetadata`, and typed `parameters`. The request cases are `.workspaceRequest`, `.command`, `.attach`, `.detach`, and `.controlRequest`. Host responses and events use `.workspaces`, `.commandResult`, `.checkpointChunk`, `.output`, `.controlState`, `.activity`, and `.error`; `.input` and `.resize` require a current controller lease and terminal generation. Detaching removes that connection's subscription and control without stopping the terminal. A lease belongs to the trusted WebSocket source connection ID so separate scenes on one device cannot control the same terminal at once. The `.takeover` action creates a new lease and invalidates the prior controller.

`ControlStateParameters` publishes the terminal generation and authoritative rows and columns with the current connection-scoped lease. This lets spectators render the host's actual grid while only the controller sends size changes.

`CommandOperation` covers workspace, folder, and tab creation, rename, close, reorder, pin, color, and move operations. It also covers tab move and split, settings patches, mark-read, notification grant registration, and terminal image paste. Small images use one bounded payload. Larger PNG and JPEG data uses ordered 64 KiB chunks with an 8 MiB transfer limit and explicit cancellation at the app edge. `CommandParameters.payload` remains a bounded opaque encoding owned by `MyTermCore`.

Terminal checkpoints use `CheckpointChunkParameters`. `CheckpointAssembler` accepts reordered chunks while requiring one transfer ID, runtime, session, generation, and sequence. It caps the assembled checkpoint at 32 MiB, caps concurrent transfers, rejects duplicates, and expires incomplete transfers.

## Validation

Run the macOS package suite from this directory:

```sh
swift test
```

The suite starts the production Go relay handler in a separate TLS process for native HTTP and bidirectional WebSocket coverage. Its 30 tests cover PKCE, malicious callbacks, endpoint and redirect rules, token refresh rotation, pairing, HPKE tamper and replay rejection, typed JSON, framing, checkpoint limits, connection generations, controller leases, and the push SDK's storage and cryptography boundaries.
